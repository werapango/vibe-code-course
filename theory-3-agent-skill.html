WBS: จาก SPEC สู่ TASKS

WBS (Work Breakdown Structure) คือการแตกงานเป็นลำดับชั้น Epic → Task จนชิ้นเล็กพอให้ทำและตรวจได้ทีละชิ้น ตัวอย่างจาก TASKS.md ของ baseline:

## Epic 1: รถส่วนกลาง (US-1)
- [ ] T1.1 migration 0002_cars.sql + API src/routes/cars.ts + เคส smoke — AC-1.1 – AC-1.6
- [ ] 👤 migrations apply --local → npm run smoke → npm run trace → commit
- [ ] T1.2 หน้าเว็บ "รถ" ใน public/ — depends: T1.1

## Epic 2: การจอง (US-2, US-3, US-4)
- [ ] T2.1 migration 0003_bookings.sql + POST /api/bookings + smoke ตามตารางตัวอย่าง #1–#8
- [ ] T2.2 GET การจองของฉัน + DELETE ของฉัน — depends: T2.1
- [ ] T2.3 GET /api/cars/:id/schedule — depends: T2.1
- [ ] T2.4 หน้าเว็บจองรถ + การจองของฉัน — depends: T2.2, T2.3
หลักความหมายในหลักสูตร
1 task = 1 promptแก้ 1–3 ไฟล์ จบในรอบเดียวสั่ง ทำ task T1.1 ใน TASKS.md — prompt สั้น เพราะรายละเอียดอยู่ใน SPEC
กฎ 100%task ทั้งหมดรวมกัน = ขอบเขตทั้งหมดพอดี ไม่ขาดไม่เกินAC ทุกข้อของ Release 1 ต้องมี task รับผิดชอบ · ไม่มี task ที่ทำ FR “ยังไม่ทำ”
ตรวจได้ทุก task ผูกกับ ACจบ task = smoke + trace บอกผลได้ทันที
รู้ลำดับdepends onต้องมีตาราง cars ก่อน bookings · API ก่อนหน้าเว็บ
งานของคนคั่น👤 ระหว่าง taskmigration, smoke, trace, อ่าน git diff, commit — agent ไม่ทำแทน

Agent ทำงานอย่างไร

LLMสมองที่คิดและเขียน
+
Toolsอ่าน/แก้ไฟล์, รันคำสั่ง
+
Loopวางแผน → ลงมือ → ดูผล → ซ้ำ
+
Contextทุกอย่างที่มันอ่านใน session นี้

นึกถึง Lab 1a: ZCode วางแผน → สร้างไฟล์ → ตรวจ/สรุป — นั่นคือ agent loop สิ่งสำคัญคือ agent ไม่มีความจำข้าม session มันรู้แค่สิ่งที่อยู่ใน context ตอนนั้น

🪙 context = เงิน

ทุกไฟล์ที่ agent อ่าน ทุกข้อความใน session ทุกผลลัพธ์ของคำสั่ง ถูกนับเป็น token ทุกรอบของ loop session ยาว + log ยาว + ไฟล์ไม่เกี่ยว = จ่ายแพงขึ้นเรื่อย ๆ · จึงมีกติกา: 1 task ต่อ prompt, จบ lab เปิด session ใหม่, แปะเฉพาะบรรทัด error ที่เกี่ยว

Guardrails: ทำไม agent ห้ามรันคำสั่ง

AGENTS.md ของ starter เขียนไว้ว่า ห้ามรัน wrangler, npm install, git เอง ให้เขียนคำสั่งไว้ท้ายคำตอบแทน เหตุผล 3 ข้อ:

  1. ความปลอดภัย — migrations apply --remote, deploy, d1 execute แตะข้อมูลจริง การตัดสินใจนี้ต้องเป็นของคน
  2. token — ผลของคำสั่ง (log ติดตั้ง, ตาราง migration) ยาวมาก ถ้า agent รันเองจะไหลเข้า context ทุกรอบ
  3. ความเข้าใจ — คนที่รันคำสั่งเองรู้ว่าระบบอยู่ในสถานะไหน (local/remote, migrate แล้วหรือยัง)

ADLC: วงจรการพัฒนา agent/skill

คำว่า ADLC ใช้เรียก “Agent Development Life Cycle” — ยังไม่มีมาตรฐานเดียว แต่แนวคิดหลักคือ: AGENTS.md และ skill ก็เป็น “ซอฟต์แวร์” ที่ต้องพัฒนาเป็นวงจรเหมือนกัน

Defineagent/skill นี้ทำงานอะไร

→
Buildเขียน AGENTS.md / SKILL.md
→
Evalลองเคสตัวอย่าง ดูว่าทำตามไหม
→
Deployใช้กับงานจริง
→
Improveปรับจากที่พลาด

📖 แนวคิดหลัก

agent ไม่ได้ “ฉลาดขึ้นเอง” — มันทำได้ดีเท่ากับ spec + กติกา + ตัวอย่าง ที่เราให้ งานของคนในยุค agent คือดูแลสามอย่างนี้ให้ถูกและสั้น แล้วตรวจผลทุกครั้ง

  3. เราจะ eval skill add-endpoint อย่างไร ถ้าผลของ agent ไม่เหมือนเดิมทุกครั้ง?
