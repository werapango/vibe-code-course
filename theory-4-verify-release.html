ผ่านไม่ error ≠ ถูก

ดู query ตรวจเวลาซ้อนสองแบบนี้ — ทั้งคู่รันได้ ไม่มี error:

❌ แบบที่ดูถูก

WHERE car_id = ?
  AND start_at <= ?   -- end ใหม่
  AND end_at   >= ?   -- start ใหม่

ปฏิเสธการ “ต่อคิวพอดี” (จบ 12:00 / เริ่ม 12:00) ซึ่ง spec บอกว่าต้องจองได้

✅ แบบที่ตรง spec

WHERE car_id = ?
  AND start_at < ?    -- end ใหม่
  AND end_at   > ?    -- start ใหม่

ช่วงแบบ [เริ่ม, จบ) — ต่างกันแค่เครื่องหมาย = ตัวเดียว

📖 แนวคิดหลัก

agent เขียนโค้ดที่ “ดูเหมือนถูก” ได้เก่งมาก ความผิดแบบนี้ไม่มี error ให้เห็น — จับได้ด้วยการเทียบกับ spec เท่านั้น นี่คือเหตุผลที่ตารางตัวอย่าง #1–#8 ใน SPEC มีเคส “ต่อคิวพอดี” อยู่ด้วย

อ่าน diff และวงจรดีบั๊ก

git diff คือ code review ยุค agent — อ่านก่อน commit ทุกครั้ง ดูแค่ 3 เรื่องก็พอ:

  • แก้เฉพาะไฟล์ที่ task บอกไหม (ไม่แตะ auth.ts ถ้าไม่ได้สั่ง)
  • มี SQL ต่อ string ไหม · มี query ของข้อมูลผู้ใช้ที่ไม่กรอง user_id ไหม
  • ทำเกิน task ไหม (เพิ่ม dependency, ทำฟีเจอร์ที่อยู่ใน “ยังไม่ทำ”) → git restore . แล้วสั่งใหม่

→

→

→

Auth ของ starter ใน 5 แนวคิด

ระบบผู้ใช้มากับ starter ตั้งแต่ Lab 1b — งานของเราคืออ่านให้เข้าใจและตรวจให้ได้ โค้ดจริงจาก src/lib/auth.ts:

1 · Authentication ≠ Authorization

Authentication = คุณคือใคร (ล็อกอิน → 401 ถ้าไม่รู้ว่าเป็นใคร) · Authorization = คุณทำสิ่งนี้ได้ไหม (403 ถ้ารู้ว่าเป็นใครแต่ไม่มีสิทธิ์)

// authorization: ต้องเป็น admin (ใช้ต่อจาก requireAuth เสมอ)
export const requireAdmin: MiddlewareHandler<AppEnv> = async (c, next) => {
  if (c.get("role") !== "admin") return c.json({ error: "เฉพาะผู้ดูแลระบบเท่านั้น" }, 403);
  await next();
};

อีกรูปของ authorization คือ “ข้อมูลเป็นของใคร” — DELETE FROM bookings WHERE id = ? AND user_id = ?

2 · ไม่เก็บรหัสผ่าน เก็บ hash + salt

const ITERATIONS = 100_000; // ค่าสูงสุดที่ Workers รองรับ
export async function hashPassword(password: string): Promise<string> {
  const salt = crypto.getRandomValues(new Uint8Array(16));
  return toHex(salt) + ":" + (await pbkdf2(password, salt));
}

PBKDF2 ตั้งใจให้ช้า (เดารหัสทีละล้านครั้งยาก) · salt สุ่มต่อผู้ใช้ ทำให้รหัสเดียวกันได้ hash ต่างกัน · ตรวจได้ด้วยการเปิดตาราง users (inspection)

3 · Session: บัตรผ่านชั่วคราว

const token = toHex(crypto.getRandomValues(new Uint8Array(32)));
const expiresAt = new Date(Date.now() + SESSION_DAYS * 86_400_000).toISOString();

ล็อกอินสำเร็จ → token สุ่มเดาไม่ได้ เก็บในตาราง sessions หมดอายุ 7 วัน · logout หรือ admin ตั้งรหัสใหม่ = ลบ session ทิ้งฝั่งเซิร์ฟเวอร์

4 · Cookie HttpOnly

return { httpOnly: true, secure: new URL(c.req.url).protocol === "https:",
         sameSite: "Lax" as const, path: "/", maxAge: SESSION_DAYS * 86_400 };

JavaScript ในหน้าเว็บอ่าน cookie นี้ไม่ได้ → ขโมยผ่านสคริปต์แปลกปลอม (XSS) ยากขึ้น · ดูได้ที่ F12 → Application → Cookies

5 · เซิร์ฟเวอร์เช็กทุกคำขอ

bookings.use("*", requireAuth); // ทุก route ด้านล่างต้องล็อกอิน

ซ่อนปุ่มในหน้าเว็บไม่ใช่ความปลอดภัย — ใครก็เรียก API ตรงได้ ด่านจริงอยู่ที่เซิร์ฟเวอร์ทุกคำขอ

⚠ ความเสี่ยงของหน้า “ตั้งค่าครั้งแรก”

หลัง deploy ครั้งแรก ใครที่รู้ URL ก่อนจะสร้าง admin คนแรกได้ — จึงต้องเปิด URL และสร้าง admin ทันทีหลัง deploy (ทำแล้วใน Lab 1b) นี่คือตัวอย่างว่าความปลอดภัยไม่ได้อยู่แค่ในโค้ด แต่อยู่ในขั้นตอนการ release ด้วย

ทำไมยังไม่พร้อม production

ระบบนี้ทำไว้เพื่อการเรียน — สิ่งที่ขาดเขียนเป็น NFR สำหรับรอบถัดไปได้ทันที:

ที่ขาดเสี่ยงอะไรNFR ที่ควรเขียน (วัดได้)
จำกัดจำนวนครั้งที่ล็อกอินผิดถูกเดารหัสแบบอัตโนมัติล็อกอินผิด 5 ครั้งใน 15 นาที → ระงับชื่อนั้น 15 นาที
รีเซ็ตรหัสด้วยตัวเองลืมรหัสต้องพึ่ง adminผู้ใช้รีเซ็ตรหัสผ่านลิงก์ทางอีเมลที่หมดอายุใน 30 นาที
เทียบ hash แบบ constant-timetiming attack (ทางทฤษฎี)การตรวจรหัสใช้เวลาเท่ากันไม่ว่าถูกหรือผิด
บันทึกเหตุการณ์ (audit log)ไม่รู้ว่าใครลบ/แก้อะไรทุกการลบรถ/ผู้ใช้ บันทึกผู้ทำและเวลา เก็บ 90 วัน
2 คำขอพร้อมกันเป๊ะ (race)อาจได้การจองซ้อน 1 คู่ไม่มีการจองซ้อนแม้ส่งคำขอพร้อมกัน 10 รายการ

Release: migration, deploy, rollback, log

Migration เดินหน้าอย่างเดียว

schema เปลี่ยน = ไฟล์ migration ใหม่ ห้ามแก้ไฟล์เก่า เพราะ local และ production บันทึกไว้แล้วว่ารันไฟล์ไหนไปแล้ว — แก้ไฟล์เก่า = สองที่ไม่ตรงกันอย่างเงียบ ๆ

→

4smoke กับ production
→

ข้อควรรู้: rollback ย้อนโค้ด ไม่ได้ย้อนฐานข้อมูล — migration ที่รันบน remote แล้วยังอยู่ จึงควรออกแบบ migration ให้โค้ดเวอร์ชันก่อนยังทำงานได้ (เช่น เพิ่มตาราง/คอลัมน์ ไม่ลบ) · ใน PowerShell ตั้งตัวแปรด้วย $env:BASE_URL="..."; npm run smoke

Token economics: ทบทวนทั้งวัน

งานใครทำทำไม
คำสั่ง Cloudflare (dev, d1, migrate, deploy, rollback)คนสั้น แม่นยำ ผลยาวไม่ควรเข้า context ของ agent
ร่าง SRS / designGemini / ChatGPTฟรี ไม่ใช้โควต้า ZCode · คน validate
เขียนโค้ดทีละ taskZCode Flashspec ชัด + ตัวอย่างโค้ดในโปรเจกต์ = จบในรอบเดียว
บั๊กที่ Flash แก้ไม่ตก 2 รอบZCode GLM-5.3แปะสรุปสิ่งที่ลองแล้ว ไม่เริ่มใหม่จากศูนย์

ประมาณการทั้งวัน ~0.3–0.5M token ของ ZCode ต่อคน (ยังไม่ได้วัดจากห้องจริง) เทียบกับโควต้าฟรี GLM-5.3 ~3M + Flash ~5M

คำถามชวนคุย

  1. smoke ผ่าน 100% และ trace ครบ แต่ผู้ใช้บอกว่า “ไม่ใช่ที่ต้องการ” — เกิดได้อย่างไร? ผิดที่ phase ไหน?
  2. ถ้าซ่อนปุ่ม “ลบรถ” ในหน้าเว็บของผู้ใช้ทั่วไปแล้ว ยังต้องมี requireAdmin ที่เซิร์ฟเวอร์อีกไหม? ทำไม?
  3. deploy แล้วพัง กด rollback แล้วยังพัง — สาเหตุน่าจะอยู่ที่อะไร?

✅ สรุป 3 บรรทัด
  • รันได้ไม่เท่ากับถูก — smoke ตรวจตาม AC, trace ตรวจว่าไม่มี AC ตกหล่น, การตรวจรับกับผู้ใช้คือ validation

  • release ปลอดภัย: smoke local → migrate remote → deploy → smoke production → rollback ได้ (แต่ฐานข้อมูลไม่ย้อน)
บันทึกผู้สอน
