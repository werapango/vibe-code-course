รันได้ไม่มี error ไม่ได้แปลว่าถูก

ดู query ตรวจเวลาซ้อนสองแบบนี้ — ทั้งคู่รันได้ ไม่มี error:

❌ แบบที่ดูเหมือนถูก

WHERE car_id = ?
  AND start_at <= ?   -- end ใหม่
  AND end_at   >= ?   -- start ใหม่

แบบนี้จะไม่ยอมให้จอง “ต่อคิวพอดี” (รถคันเดียวกัน คนแรกจบ 12:00 คนถัดไปเริ่ม 12:00) ทั้งที่ spec บอกว่าต้องจองได้

✅ แบบที่ตรง spec

WHERE car_id = ?
  AND start_at < ?    -- end ใหม่
  AND end_at   > ?    -- start ใหม่

นับช่วงเวลาแบบ [เริ่ม, จบ) คือรวมเวลาเริ่ม แต่ไม่รวมเวลาจบ — ต่างจากแบบแรกแค่เครื่องหมาย = ตัวเดียว

อ่าน diff และวงจรดีบั๊ก

git diff แสดงว่าโค้ดเปลี่ยนไปตรงไหนบ้าง การอ่าน diff จึงเป็นการรีวิวโค้ดที่ agent เขียน ให้อ่านก่อน commit (บันทึกการเปลี่ยนแปลงลง git) ทุกครั้ง โดยดูแค่ 3 เรื่องก็พอ:

  • แก้เฉพาะไฟล์ที่ task บอกไหม (ไม่แตะ auth.ts ถ้าไม่ได้สั่ง)
  • มี SQL ที่เอาข้อความมาต่อกันเอง ไหม (เสี่ยงถูกแทรกคำสั่ง SQL) และมี query ข้อมูลผู้ใช้ที่ไม่กรอง user_id ไหม (คนอื่นจะเห็นข้อมูลของเรา)
  • ทำเกิน task ไหม (เช่น เพิ่ม dependency หรือทำฟีเจอร์ที่ SPEC ระบุว่า “ยังไม่ทำ”) ถ้าเกิน ให้รัน git restore . เพื่อทิ้งการแก้ทั้งหมด แล้วสั่งใหม่

Auth ของ starter ใน 5 แนวคิด

auth คือระบบล็อกอินและสิทธิ์ของผู้ใช้ ซึ่งมากับ starter (โปรเจกต์ตั้งต้น) ตั้งแต่ Lab 1b งานของเราคืออ่านให้เข้าใจและตรวจให้ได้ ตัวอย่างข้างล่างเป็นโค้ดจริงจาก src/lib/auth.ts:

1 · Authentication กับ Authorization ไม่เหมือนกัน

Authentication (ยืนยันตัวตน) คือตรวจว่าคุณเป็นใคร ถ้ายังไม่ได้ล็อกอิน เซิร์ฟเวอร์ตอบรหัส 401 Authorization (ตรวจสิทธิ์) คือตรวจว่าคุณทำสิ่งนี้ได้ไหม ถ้ารู้ว่าเป็นใครแต่ไม่มีสิทธิ์ เซิร์ฟเวอร์ตอบรหัส 403

// authorization: ต้องเป็น admin (ใช้ต่อจาก requireAuth เสมอ)
export const requireAdmin: MiddlewareHandler<AppEnv> = async (c, next) => {
  if (c.get("role") !== "admin") return c.json({ error: "เฉพาะผู้ดูแลระบบเท่านั้น" }, 403);
  await next();
};

อีกรูปของ authorization คือ “ข้อมูลเป็นของใคร” — DELETE FROM bookings WHERE id = ? AND user_id = ?

2 · ไม่เก็บรหัสผ่าน เก็บ hash + salt

const ITERATIONS = 100_000; // ค่าสูงสุดที่ Workers รองรับ
export async function hashPassword(password: string): Promise<string> {
  const salt = crypto.getRandomValues(new Uint8Array(16));
  return toHex(salt) + ":" + (await pbkdf2(password, salt));
}

hash คือการแปลงรหัสผ่านเป็นข้อความที่แปลงกลับไม่ได้ ส่วน salt คือค่าสุ่มที่เติมให้ผู้ใช้แต่ละคน ทำให้รหัสเดียวกันได้ hash ต่างกัน PBKDF2 (วิธี hash ที่ใช้) ตั้งใจให้ช้า คนร้ายจึงลองเดารหัสเป็นล้านครั้งได้ยาก ตรวจด้วยตาได้โดยเปิดตาราง users ดูว่าไม่มีรหัสผ่านจริงเก็บอยู่

3 · Session: สถานะการล็อกอิน

const token = toHex(crypto.getRandomValues(new Uint8Array(32)));
const expiresAt = new Date(Date.now() + SESSION_DAYS * 86_400_000).toISOString();

session คือสถานะ “ล็อกอินอยู่” เมื่อล็อกอินสำเร็จ เซิร์ฟเวอร์สร้าง token (ในที่นี้คือรหัสสุ่มยาวที่เดาไม่ได้ คนละความหมายกับ token ของ AI) เก็บในตาราง sessions และหมดอายุใน 7 วัน เมื่อ logout หรือ admin ตั้งรหัสผ่านใหม่ให้ เซิร์ฟเวอร์จะลบ session นั้นทิ้ง

4 · Cookie HttpOnly

return { httpOnly: true, secure: new URL(c.req.url).protocol === "https:",
         sameSite: "Lax" as const, path: "/", maxAge: SESSION_DAYS * 86_400 };

cookie คือข้อมูลเล็ก ๆ ที่เบราว์เซอร์เก็บไว้และส่งกลับไปกับทุกคำขอ (ที่นี่ใช้เก็บ token ของ session) ค่า HttpOnly ทำให้ JavaScript ในหน้าเว็บอ่าน cookie นี้ไม่ได้ สคริปต์แปลกปลอมที่ถูกแอบฝังในหน้าเว็บ (XSS) จึงขโมยได้ยากขึ้น ลองดูได้โดยกด F12 แล้วไปที่ Application → Cookies

5 · เซิร์ฟเวอร์เช็กทุกคำขอ

bookings.use("*", requireAuth); // ทุก route ด้านล่างต้องล็อกอิน

ซ่อนปุ่มในหน้าเว็บไม่ใช่ความปลอดภัย — ใครก็เรียก API ตรงได้ การตรวจสิทธิ์จึงต้องทำที่เซิร์ฟเวอร์ทุกคำขอ

⚠ ความเสี่ยงของหน้า “ตั้งค่าครั้งแรก”

หลัง deploy ครั้งแรก ใครที่รู้ URL ก่อนจะสร้าง admin คนแรกได้ — จึงต้องเปิด URL และสร้าง admin ทันทีหลัง deploy (ทำแล้วใน Lab 1b) นี่คือตัวอย่างว่าความปลอดภัยไม่ได้อยู่แค่ในโค้ด แต่อยู่ในขั้นตอนการ release ด้วย

ทำไมยังไม่พร้อม production

ระบบนี้ทำไว้เพื่อการเรียน สิ่งที่ยังขาดเอาไปเขียนเป็น NFR (ความต้องการด้านคุณภาพ เช่น ความปลอดภัย ความเร็ว) สำหรับรอบถัดไปได้ทันที:

ที่ขาดเสี่ยงอะไรNFR ที่ควรเขียน (วัดได้)
จำกัดจำนวนครั้งที่ล็อกอินผิดถูกเดารหัสแบบอัตโนมัติล็อกอินผิด 5 ครั้งใน 15 นาที → ระงับชื่อนั้น 15 นาที
รีเซ็ตรหัสด้วยตัวเองลืมรหัสต้องพึ่ง adminผู้ใช้รีเซ็ตรหัสผ่านลิงก์ทางอีเมลที่หมดอายุใน 30 นาที
เทียบ hash โดยใช้เวลาคงที่ (constant-time)คนร้ายจับเวลาการตอบเพื่อเดารหัส (timing attack — เสี่ยงในทางทฤษฎี)การตรวจรหัสใช้เวลาเท่ากันไม่ว่าถูกหรือผิด
บันทึกเหตุการณ์ (audit log)ไม่รู้ว่าใครลบ/แก้อะไรทุกการลบรถ/ผู้ใช้ บันทึกผู้ทำและเวลา เก็บ 90 วัน
รับมือ 2 คำขอที่มาพร้อมกันพอดี (race condition)อาจได้การจองซ้อน 1 คู่ไม่มีการจองซ้อนแม้ส่งคำขอพร้อมกัน 10 รายการ

Release: migration, deploy, rollback, log

Migration: เพิ่มไฟล์ใหม่เท่านั้น ไม่แก้ไฟล์เก่า

migration คือไฟล์ SQL ที่เปลี่ยนโครงสร้างตาราง (schema) ทุกครั้งที่ต้องเปลี่ยน schema ให้สร้างไฟล์ migration ใหม่ ห้ามแก้ไฟล์เก่า เพราะทั้ง local (เครื่องเรา) และ production (ระบบจริง) จดไว้แล้วว่ารันไฟล์ไหนไปแล้ว ถ้าไปแก้ไฟล์เก่า ฐานข้อมูลสองที่จะไม่ตรงกันโดยไม่มีอะไรเตือน

ลำดับ release (deploy = นำโค้ดขึ้นระบบจริง, rollback = ย้อนกลับไปเวอร์ชันก่อน)

  3. deploy แล้วพัง กด rollback แล้วยังพัง — สาเหตุน่าจะอยู่ที่อะไร?

ใน Lab 4 (30 นาที) คุณจะทำเช็กลิสต์ตรวจ auth และ NFR บน production จากนั้นจับคู่กับเพื่อนที่เล่นบท “ผู้ใช้” ตรวจรับเทียบกับโจทย์ต้นฉบับ แยกสิ่งที่เจอว่าเป็น bug หรือ requirement gap แล้ว release และติดป้ายเวอร์ชันด้วย git tag v1.0 กลุ่มที่เสร็จเร็วลองทำ change request (คำขอเปลี่ยนแปลง FR-11/FR-12) หรือหาบั๊กที่ผู้สอนใส่ไว้ในระบบ ก่อนกลับอย่าลืมออกจากระบบ (log out) ทุกบริการ

✅ สรุป 3 บรรทัด
  • รันได้ไม่ได้แปลว่าถูก — smoke ตรวจตาม AC, trace ตรวจว่าไม่มี AC ตกหล่น, การตรวจรับกับผู้ใช้คือ validation
  • auth ประกอบด้วย ยืนยันตัวตน (401), ตรวจสิทธิ์ (403 และกรอง user_id), เก็บรหัสเป็น hash+salt, session, cookie แบบ HttpOnly และเซิร์ฟเวอร์เช็กทุกคำขอ
  • release อย่างปลอดภัย: smoke ใน local → migrate บน remote → deploy → smoke บน production → ถ้าพังก็ rollback ได้ (แต่ฐานข้อมูลไม่ย้อนตาม)
บันทึกผู้สอน
  • เปิดด้วยสอง query เวลาซ้อน — ถามห้องว่า “ต่างกันตรงไหน” ก่อนเฉลย
  • หัวข้อ auth: ไม่ต้องอ่านโค้ดทุกบรรทัด ชี้ 5 จุดแล้วโยงกับเช็กลิสต์ Lab 4
  • ถ้าห้องตามช้า ย่อหัวข้อ “ยังไม่พร้อม production” เหลืออ่านตาราง และข้าม token economics
