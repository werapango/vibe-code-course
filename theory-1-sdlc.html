Vibe coding → Agentic engineering

Vibe coding คือการบอก AI ด้วยภาษาธรรมชาติแล้ว “รับของที่ได้” โดยแทบไม่อ่านโค้ด — เร็วมาก และเหมาะกับต้นแบบหรือของใช้ครั้งเดียว whitepaper ของ Google The New SDLC With Vibe Coding (หน้า 10–14) มองเป็น spectrum สามระดับ:

มิติVibe codingStructured AI-assistedAgentic engineering
ระบุความต้องการประโยคเดียวspec สั้น + ข้อจำกัดspec เป็นเอกสาร + eval
การตรวจดูด้วยตาทดสอบทุกฟีเจอร์tests + evals อัตโนมัติ
ความเข้าใจโค้ดไม่จำเป็นอ่าน flow หลักเข้าใจเชิงสถาปัตยกรรม
เหมาะกับของเล่น, ต้นแบบฟีเจอร์จริงระบบ production

วันนี้เราจะลองซ้ายสุดก่อน (Lab 1a: สั่ง ZCode สร้างหน้าเว็บไฟล์เดียวแล้ว deploy) เพื่อสัมผัสว่ามันเร็วแค่ไหน แล้วใช้ทั้งวันที่เหลือขยับมาระดับกลาง: มี SRS, มี spec ที่ตรวจได้, มี WBS, มี test, มี checkpoint

SDLC: 6 phase และชิ้นงานของแต่ละ phase

SDLC (Software Development Life Cycle) คือวงจรที่ทุกซอฟต์แวร์ต้องผ่าน ไม่ว่าจะใช้ AI หรือไม่ หัวใจคือทุก phase มีชิ้นงานที่ตรวจได้

1 Requirementsต้องการอะไร
→
2 Designสร้างอย่างไร
→
3 Implementationเขียนโค้ด
→
4 Testingถูกจริงไหม
→
5 Deploymentส่งมอบ
→
6 Maintenanceดูแล/ปรับ
Phaseคำถามหลักชิ้นงานวันนี้
Requirementsใครใช้ ต้องการอะไร วัดความสำเร็จอย่างไรdocs/SRS.md · user story + AC ใน SPEC.md
Designสถาปัตยกรรม ข้อมูล API เลือกอะไรเพราะอะไรdocs/DESIGN.md (ADR, data model, API contract)
Implementationแตกงานแล้วสร้างทีละชิ้นTASKS.md (WBS) · โค้ดใน src/, public/, migrations/
Testingตรงตาม AC ไหม ตามรอยครบไหมnpm run smoke · npm run trace · เช็กลิสต์
Deploymentขึ้น production อย่างปลอดภัย ถอยกลับได้ไหมwrangler deploy · rollback · URL จริง
Maintenanceรู้ไหมว่าพัง แก้ได้เร็วไหมwrangler tail · git history · backlog รอบถัดไป

Waterfall เดินครบทีละ phase ครั้งเดียว · Agile/iterative วนรอบสั้น ๆ หลายรอบ — วันนี้เราวน 1 รอบเต็มแบบย่อ และจบด้วย backlog สำหรับรอบถัดไป

AI-native SDLC: คอขวดย้ายไปไหน

AI บีบเวลาทุก phase แต่บีบไม่เท่ากัน (whitepaper หน้า 19–25):

PhaseAI ช่วยได้สิ่งที่ยังต้องเป็นคน
Requirementsช่วยตั้งคำถาม ร่างเอกสารเร็วยืนยันกับเจ้าของโจทย์ — AI ไม่รู้ปัญหาของหน่วยงานเรา และมัก “แต่ง” requirement อย่างมั่นใจ
Designเสนอ schema / API / ทางเลือกเลือกทางเลือก บันทึกเหตุผล (ADR)
Implementationมากที่สุด — เขียนเร็วกว่าคนหลายเท่าแตกงานให้พอดี อ่าน diff
Testingเขียน test ให้ได้ตัดสินว่าผลถูกไหม — AI ตรวจงานตัวเองแล้วมักเชื่อตัวเอง
Deploymentอ่าน error ช่วยวินิจฉัยกด deploy รับผิดชอบ production
📖 แนวคิดหลัก: คอขวดย้ายที่

เมื่อการเขียนโค้ดเกือบฟรี สิ่งที่แพงขึ้นคือ (1) บอกให้ชัดว่าต้องการอะไร และ (2) ตรวจว่าที่ได้มาถูกจริง whitepaper สรุปว่า “Verification, judgment, and direction are the new craft.” (หน้า 48) วันนี้จึงใช้เวลากับ SRS, spec ที่ตรวจได้, WBS และการตรวจรับ มากกว่าการพิมพ์ prompt

🪙 ทำไมเรื่องนี้เกี่ยวกับ token

ทุกครั้งที่ agent ต้องเดาว่าเราต้องการอะไร หรือวนแก้ config ที่คนรันเองได้ในคำสั่งเดียว เราจ่าย token วันนี้จึงแบ่งงาน: คนรันคำสั่ง Cloudflare เอง · SRS/design ร่างกับ Gemini/ChatGPT (ไม่ใช้โควต้า ZCode) · ZCode เขียนโค้ดทีละ task จาก spec ที่ชัดแล้ว

ระบบเว็บในหนึ่งภาพ: client–server, local–production

Clientเบราว์เซอร์ · public/
⇄ HTTP
ServerWorker + Hono · src/
⇄
DatabaseD1 · migrations/
  • client ส่ง request (method + path + body) · server ตอบ status code + JSON เช่น 200 สำเร็จ, 201 สร้างแล้ว, 400 ข้อมูลผิด, 401 ยังไม่ล็อกอิน, 403 ไม่มีสิทธิ์, 404 ไม่พบ, 409 ขัดแย้ง (เช่น ซ้ำ/ซ้อน)
  • local = npm run dev บนเครื่องเรา ฐานข้อมูลจำลองใน .wrangler/ · production = wrangler deploy ขึ้น Cloudflare ฐานข้อมูลจริงอีกก้อน — สองที่นี้แยกกัน ต้อง migrate ทั้งคู่

ไม่ต้องจำตอนนี้ — Lab 1b จะให้เห็นของจริงทั้งหมด (F12 → Network, /api/health, local vs production, rollback)

☁️ แต่ละกล่องคือบริการไหนของ Cloudflare

Worker = Workers · ไฟล์หน้าเว็บ = Static Assets · ฐานข้อมูล = D1 · URL = workers.dev · สั่งทั้งหมดด้วย wrangler — อธิบายละเอียด พร้อมโควตาฟรีและสิ่งที่ไม่ต้องกด ใน Cloudflare ที่ใช้ในหลักสูตร

เชื่อมกับ Lab

Lab 1 มี 2 ช่วง: 1a ลอง vibe coding จริง (ZCode สร้างหน้าเว็บไฟล์เดียว → deploy คำสั่งเดียว) แล้วถามตัวเองว่า “วิธีนี้พอสำหรับระบบจริงไหม” จากนั้น 1b เริ่มจาก starter ที่มีฐานข้อมูลและระบบผู้ใช้ — deploy, สร้าง admin, ลอง rollback และดู log สด โดยไม่ใช้ token

✅ สรุป 3 บรรทัด
  • SDLC = Requirements → Design → Implementation → Testing → Deployment → Maintenance และทุก phase มีชิ้นงานที่ตรวจได้
  • AI เร่ง Implementation มากที่สุด คอขวดจึงย้ายไปอยู่ที่ spec และ verification ซึ่งยังต้องเป็นคน
  • วันนี้: เช้าเราเป็นเจ้าของ requirements/design · 13:00 ตกลง baseline · บ่ายให้ agent สร้างตาม spec แล้วตรวจรับ

  • ช่วงนี้สั้น (20 นาที) — เน้นตาราง “วันนี้เดินวงจรอย่างไร” ให้ผู้เรียนเห็นภาพรวม ไม่ต้องลงรายละเอียด HTTP (Lab 1b สาธิต)
