จาก Vibe coding ถึง Agentic engineering

Vibe coding คือการสั่ง AI ด้วยภาษาธรรมชาติแล้วนำผลที่ได้ไปใช้เลย โดยแทบไม่อ่านโค้ด — เร็วมาก และเหมาะกับงานต้นแบบหรืองานที่ใช้ครั้งเดียว whitepaper ของ Google The New SDLC With Vibe Coding (หน้า 10–14) แบ่งวิธีใช้ AI เขียนโค้ดเป็นสามระดับ ไล่จาก “ปล่อยให้ AI ทำเกือบหมด” ไปจนถึง “คนวางแผนและตรวจอย่างเป็นระบบ”:

เรื่องVibe codingStructured AI-assisted (ใช้ AI แบบมีขั้นตอน)Agentic engineering (ให้ agent ทำงานแบบวิศวกรรม)
ระบุความต้องการประโยคเดียวspec สั้น + ข้อจำกัดspec เป็นเอกสารเต็ม + ชุดวัดผลอัตโนมัติ (eval)
การตรวจดูด้วยตาทดสอบทุกฟีเจอร์test และ eval รันเองอัตโนมัติ
ความเข้าใจโค้ดไม่จำเป็นอ่านลำดับการทำงานหลักเข้าใจโครงสร้างทั้งระบบ
เหมาะกับงานทดลอง, ต้นแบบฟีเจอร์จริงระบบที่มีผู้ใช้จริงจำนวนมาก (production)

วันนี้เราจะลองระดับแรก (Vibe coding) ก่อน (Lab 1a: สั่ง ZCode สร้างหน้าเว็บไฟล์เดียวแล้ว deploy) เพื่อให้เห็นว่าเร็วแค่ไหน แล้วใช้เวลาที่เหลือของวันฝึกระดับกลาง (ใช้ AI แบบมีขั้นตอน): มีเอกสารความต้องการ (SRS), มี spec ที่ตรวจได้, มีรายการแตกงาน (WBS), มี test และมีจุดหยุดตรวจงาน (checkpoint)

SDLC: 6 phase และชิ้นงานของแต่ละ phase

SDLC (Software Development Life Cycle) คือวงจรที่ทุกซอฟต์แวร์ต้องผ่าน ไม่ว่าจะใช้ AI หรือไม่ แบ่งเป็นขั้นตอนย่อยเรียกว่า phase สิ่งสำคัญคือทุก phase ต้องมีชิ้นงานที่คนอื่นหยิบมาตรวจได้

1 Requirementsต้องการอะไร
→
2 Designสร้างอย่างไร
→
3 Implementationเขียนโค้ด
→
4 Testingถูกจริงไหม
→
5 Deploymentส่งมอบ
→
6 Maintenanceดูแล/ปรับ
Phaseคำถามหลักชิ้นงานวันนี้
Requirementsใครใช้ ต้องการอะไร วัดความสำเร็จอย่างไรdocs/SRS.md · user story (ความต้องการเล่าจากมุมผู้ใช้) + AC (เกณฑ์ตรวจรับ) ใน SPEC.md
Designระบบมีส่วนประกอบอะไร เก็บข้อมูลแบบไหน API หน้าตาอย่างไร และเลือกแบบนี้เพราะอะไรdocs/DESIGN.md (ADR = บันทึกเหตุผลการตัดสินใจ, data model = โครงสร้างข้อมูล, API contract = ข้อตกลงหน้าตา API)
Implementationแตกงานแล้วสร้างทีละชิ้นTASKS.md (WBS) · โค้ดใน src/, public/, migrations/
Testingทำงานตรงตาม AC ไหม และทุก requirement มี test รองรับครบไหมnpm run smoke · npm run trace · เช็กลิสต์
Deploymentนำขึ้นระบบจริง (production) อย่างปลอดภัยไหม ถ้าพังย้อนกลับเวอร์ชันเดิมได้ไหมwrangler deploy · rollback · URL จริง
Maintenanceถ้าระบบพังเราจะรู้ไหม และแก้ได้เร็วแค่ไหนwrangler tail · git history · backlog (รายการงานที่เหลือ) รอบถัดไป

แบบ Waterfall ทำครบทีละ phase ตามลำดับเพียงรอบเดียว ส่วนแบบ Agile/iterative ทำเป็นรอบสั้น ๆ แล้ววนซ้ำหลายรอบ — วันนี้เราวน 1 รอบเต็มแบบย่อ และจบด้วย backlog สำหรับรอบถัดไป

SDLC ยุค AI: AI ช่วยแต่ละ phase ได้แค่ไหน และ ADLC

AI ช่วยลดเวลาได้ทุก phase แต่ลดได้ไม่เท่ากัน ส่วนที่ใช้เวลามากที่สุดของงานจึงเปลี่ยนไปจากเดิม (whitepaper หน้า 19–25):

PhaseAI ช่วยได้สิ่งที่ยังต้องเป็นคน
Requirementsช่วยตั้งคำถาม ร่างเอกสารเร็วยืนยันกับเจ้าของโจทย์ — AI ไม่รู้ปัญหาของหน่วยงานเรา และมักเขียน requirement ที่ไม่มีใครพูดไว้ขึ้นมาเองอย่างมั่นใจ
Designเสนอ schema / API / ทางเลือกเลือกทางเลือก บันทึกเหตุผล (ADR)
Implementationมากที่สุด — เขียนเร็วกว่าคนหลายเท่าแบ่งงานเป็นชิ้นขนาดพอดี และอ่าน diff (ส่วนของโค้ดที่ถูกแก้) ก่อนรับงาน
Testingเขียน test ให้ได้ตัดสินว่าผลถูกไหม — ถ้าให้ AI ตรวจงานของตัวเอง มักสรุปว่าถูก
Deploymentอ่าน error ช่วยวินิจฉัยเป็นคนกด deploy (นำขึ้นระบบจริง) และรับผิดชอบเมื่อระบบจริงมีปัญหา
📖 แนวคิดหลัก: งานที่ยากไม่ใช่การเขียนโค้ดแล้ว แต่เป็นการสั่งงานและการตรวจงาน

เมื่อ AI เขียนโค้ดได้เร็วและใช้ต้นทุนน้อย งานที่ต้องใช้เวลาและความรู้มากขึ้นคือ (1) บอกให้ชัดว่าต้องการอะไร และ (2) ตรวจว่าผลที่ได้ถูกต้องจริง whitepaper สรุปว่า “Verification, judgment, and direction are the new craft.” (หน้า 48) แปลว่า การตรวจ การใช้วิจารณญาณ และการกำหนดทิศทาง คือทักษะที่นักพัฒนาต้องมีในปัจจุบัน วันนี้จึงใช้เวลากับ SRS, spec ที่ตรวจได้, WBS และการตรวจรับ มากกว่าการพิมพ์ prompt

เมื่อใช้ agent มีวงจรเพิ่มอีกหนึ่งวง: ADLC

ถ้าให้ agent ช่วยเขียนโค้ด คำสั่งและกติกาที่เราเขียนให้ agent ก็เป็นงานที่ต้องพัฒนาเหมือนกัน วงจรนี้เรียกว่า ADLC (Agent Development Life Cycle — วงจรการพัฒนา agent) ยังไม่มีนิยามมาตรฐานเดียว แต่หลักการคือ คำสั่งของ agent ต้องเขียน ลองใช้ ตรวจผล แล้วปรับปรุงเป็นรอบ ๆ แบบเดียวกับโค้ด

Defineกำหนดว่าให้ agent ทำงานอะไร
→
Designกติกา ขั้นตอน สิ่งที่ห้ามทำ
→
Buildเขียนเป็นไฟล์ AGENTS.md / SKILL.md
→
Evalลองสั่งงานหลายครั้ง ดูว่าทำตามกติกาไหม
→
Deployใช้กับงานจริง
→
Improveagent พลาดตรงไหน แก้คำสั่งตรงนั้น
SDLCADLC
พัฒนาอะไรตัวแอป (วันนี้คือระบบจองรถ)คำสั่งและกติกาของ agent
ชิ้นงานSRS, SPEC, โค้ดใน src/ public/AGENTS.md (กติกาที่ agent อ่านทุกครั้ง) และ SKILL.md (ขั้นตอนของงานที่ทำซ้ำ)
ตรวจอย่างไรtest — รันกี่ครั้งผลก็เหมือนเดิมeval — ลองหลายครั้งแล้วนับว่าทำถูกกี่ครั้ง เพราะคำตอบของ AI ไม่เหมือนเดิมทุกครั้ง
เมื่อผลผิดแก้โค้ดแก้คำสั่ง กติกา หรือเพิ่มตัวอย่าง

วันนี้ใช้ทั้งสองวงจร: AGENTS.md มากับ starter ใน Lab 1b · ทฤษฎี 3 อธิบาย agent, skill และ ADLC ละเอียดขึ้น · ใน Lab 3 ถ้า agent ทำผิดกติกาซ้ำ ๆ ให้แก้ที่ AGENTS.md ซึ่งก็คือขั้น Improve ของ ADLC

🪙 ทำไมเรื่องนี้เกี่ยวกับ token

token คือหน่วยนับปริมาณข้อความที่ AI อ่านและเขียน ยิ่งใช้มากยิ่งเปลืองโควตา ทุกครั้งที่ agent (AI ที่ลงมือแก้ไฟล์และรันคำสั่งเองได้) ต้องเดาว่าเราต้องการอะไร หรือวนแก้ไฟล์ตั้งค่า (config) ทั้งที่คนพิมพ์คำสั่งเดียวก็เสร็จ เราก็เสีย token ไปเปล่า ๆ วันนี้จึงแบ่งงาน: คนรันคำสั่ง Cloudflare เอง · SRS/design ร่างกับ Gemini/ChatGPT (ไม่ใช้โควต้า ZCode) · ZCode เขียนโค้ดทีละ task จาก spec ที่ชัดแล้ว

  • client ส่ง request (method + path + body) · server ตอบ status code + JSON เช่น 200 สำเร็จ, 201 สร้างแล้ว, 400 ข้อมูลผิด, 401 ยังไม่ล็อกอิน, 403 ไม่มีสิทธิ์, 404 ไม่พบ, 409 ขัดแย้ง (เช่น ซ้ำ/ซ้อน)
  • local คือรันบนเครื่องเราด้วย npm run dev ใช้ฐานข้อมูลจำลองใน .wrangler/ ส่วน production คือระบบจริงบน Cloudflare ที่ขึ้นด้วย wrangler deploy และใช้ฐานข้อมูลจริงอีกชุดหนึ่ง — สองที่นี้แยกกัน จึงต้องสร้างตาราง (migrate) ทั้งสองที่

ไม่ต้องจำตอนนี้ — Lab 1b จะได้ลองทำจริงทั้งหมด (F12 → Network, /api/health, local vs production, rollback)

คำถามชวนคุย

  1. เคยให้ AI เขียนงาน (โค้ด รายงาน หรืออีเมล) แล้วส่งต่อให้คนอื่นเลยโดยไม่ได้อ่านไหม? ถ้าเทียบกับ 3 ระดับในตารางแรก (Vibe coding / ใช้ AI แบบมีขั้นตอน / Agentic engineering) ตอนนั้นคุณอยู่ระดับไหน? และถ้างานนั้นผิดพลาด ใครต้องรับผิดชอบ — AI หรือคนที่ส่งงาน?
  2. ถ้าจะทำระบบจองรถของหน่วยงาน แต่ข้ามขั้น Requirements ไปสั่ง agent เขียนเลย agent อาจเดาอะไรผิดได้บ้าง? (เช่น ใครมีสิทธิ์อนุมัติ จองซ้อนเวลาได้ไหม)
  3. ทำไมแค่ “รันได้ ไม่มี error” ยังไม่พอ สำหรับระบบที่เก็บข้อมูลของคนอื่น? (เช่น คนหนึ่งอาจแอบเห็นหรือแก้ข้อมูลของอีกคนได้)

เชื่อมกับ Lab

Lab 1 มี 2 ช่วง: 1a ลอง vibe coding จริง (ZCode สร้างหน้าเว็บไฟล์เดียว → deploy คำสั่งเดียว) แล้วถามตัวเองว่า “วิธีนี้พอสำหรับระบบจริงไหม” จากนั้น 1b เริ่มจากโปรเจกต์ตั้งต้น (starter) ที่มีฐานข้อมูลและระบบผู้ใช้ให้แล้ว — deploy, สร้าง admin, ลอง rollback และดู log สด โดยไม่ใช้ token

✅ สรุป 3 บรรทัด
  • SDLC ประกอบด้วย Requirements → Design → Implementation → Testing → Deployment → Maintenance และทุก phase มีชิ้นงานที่ตรวจได้
  • AI ช่วยให้ Implementation เร็วขึ้นมากที่สุด งานที่ยังช้าและยากจึงเป็นการเขียน spec ให้ชัด และการตรวจว่าผลถูกจริง (verification) ซึ่งยังต้องเป็นคนทำ
  • วันนี้: ช่วงเช้าเราเขียน requirements และ design เอง · 13:00 ทั้งห้องตกลงใช้ spec ฉบับเดียวกัน (baseline) · ช่วงบ่ายให้ agent สร้างตาม spec แล้วเราตรวจรับ
