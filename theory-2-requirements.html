Stakeholder และการถามก่อนเขียน (elicitation)

Stakeholder คือทุกคนที่ได้รับผลจากระบบ — ไม่ใช่แค่คนกดใช้ เช่น ระบบจองรถ: เจ้าของโจทย์ (หัวหน้างาน), คนดูแลข้อมูล, พนักงานผู้จอง, และฝ่ายที่ “ไม่ได้ใช้แต่ได้รับผล” อย่างฝ่ายการเงินที่บอกว่าไม่มีงบ

Elicitation คือการถามและพูดคุยเพื่อดึงความต้องการออกมาจากคน แทนการเดาเอง โจทย์จากผู้ใช้จริงมักกำกวม เพราะผู้ใช้เขียนด้วยภาษาของงาน ไม่ใช่ภาษาของระบบ

⚠ ข้อควรระวังเมื่อใช้ AI แชต (LLM)

ถ้าแปะโจทย์ให้ Gemini/ChatGPT แล้วสั่ง “เขียน SRS ให้หน่อย” มันจะเขียนออกมาดูดีและมั่นใจมาก — รวมถึงกติกาที่ไม่มีใครเคยพูด (เช่น จองได้ไม่เกิน 4 ชั่วโมง, ต้องได้รับอนุมัติ) วิธีที่ถูกคือ ให้ AI ตั้งคำถามก่อน แล้วเราเลือกคำถามที่สำคัญไปถามเจ้าของโจทย์ ได้คำตอบแล้วจึงค่อยให้ AI ช่วยเขียน ข้อไหนยังไม่มีคนยืนยัน ให้ติดป้าย [สมมติฐาน]

Use case และ user story

Use case — มองเป็น “การใช้งานหนึ่งเรื่อง”

use case คือการเล่าทีละขั้นว่าผู้ใช้ทำงานหนึ่งเรื่องกับระบบอย่างไร เริ่มจากทำรายการ use case (UC-01, UC-02 …) แล้วเขียน use case หลัก 1 ตัวแบบเต็ม (fully dressed = ครบทุกหัวข้อ) ตัวอย่างโครงจาก SRS อ้างอิง:

UC-02 จองรถ
Actor: พนักงาน
เงื่อนไขก่อนเริ่ม: ล็อกอินแล้ว · มีรถในระบบอย่างน้อย 1 คัน
ขั้นตอนหลัก:
  1. เลือกรถ และดูตารางของรถคันนั้นในวันที่ต้องการ
  2. กรอกรายละเอียดการจอง
  3. ระบบตรวจกติกา
  4. ระบบบันทึก และแสดงใน "การจองของฉัน"
ทางเลือก / กรณีผิดปกติ:
  3a. ถ้า ... ระบบปฏิเสธพร้อมแจ้งเหตุผล → กลับไปขั้น 1
ผลลัพธ์: การจองถูกบันทึก ช่วงเวลานั้นแสดงว่า "ไม่ว่าง"

ส่วน ทางเลือก/กรณีผิดปกติ สำคัญที่สุด เพราะแต่ละข้อมักกลายเป็น requirement และเคสทดสอบ ส่วน “กรอกรายละเอียดอะไรบ้าง” และ “กติกาอะไร” คุณต้องไปถามเองใน Lab 2

User story — มองจากประโยชน์ที่ผู้ใช้ได้รับ

user story คือความต้องการ 1 ข้อที่เล่าจากมุมผู้ใช้ รูปแบบ: ในฐานะ [ใคร] ฉันต้องการ [ทำอะไร] เพื่อ [ได้ประโยชน์อะไร] และ story ที่ดีควรผ่านเกณฑ์ INVEST:

ตัวอักษรความหมายถามตัวเอง
Independentอิสระทำเรื่องนี้ได้โดยไม่ต้องรอเรื่องอื่นมากไหม
Negotiableต่อรองได้บอก “อะไร” ไม่ล็อก “วิธี” จนแก้ไม่ได้
Valuableมีคุณค่าส่วน “เพื่อ…” ชัดไหม ใครได้ประโยชน์
Estimableประเมินได้รู้พอจะบอกได้ไหมว่าใหญ่แค่ไหน
Smallเล็กพอเสร็จได้ในรอบเดียว
Testableทดสอบได้มี acceptance criteria ที่บอกผ่าน/ไม่ผ่านได้ชัด

Acceptance criteria และ Specification by Example

AC (acceptance criteria = เกณฑ์ตรวจรับ บอกว่าแบบไหนถือว่าผ่าน) เขียนแบบ Given / When / Then คือ Given = สถานการณ์ตั้งต้น, When = สิ่งที่ผู้ใช้ทำ, Then = ผลที่ตรวจได้ ตัวอย่างจริงจากโปรเจกต์ตั้งต้น (starter):

- **AC-A2.2** Given รหัสผิด หรือไม่มีชื่อนี้ When ล็อกอิน
  Then ได้ 401 ด้วยข้อความเดียวกันทั้งสองกรณี

รหัส AC ตัวหนา **AC-x.y** จะถูกใช้เป็นชื่อเคสทดสอบใน scripts/smoke.mjs แล้วคำสั่ง npm run trace จะเช็กว่า AC ทุกข้อมีเคสทดสอบครบ

Specification by Example: เขียน “ผลที่คาดหวัง” ก่อนโค้ด

กติกาที่มีหลายกรณี เขียนเป็นประโยคเดียวจะกำกวม ให้เขียนเป็นตารางตัวอย่าง แล้วเติมผลที่คาดหวังเองก่อนให้ใครเขียนโค้ด เช่น กติกา “ชื่อผู้ใช้”:

#ชื่อผู้ใช้ที่กรอกผลที่คาดหวังเหตุผล
1somchai_01รับa-z 0-9 _ ยาว 3–30
2ab400สั้นกว่า 3
3สมชาย400ไม่ใช่ a-z
4ชื่อที่มีอยู่แล้ว409ซ้ำ

ใน Lab 2 คุณจะทำตารางแบบนี้กับกติกาที่ยากที่สุดของระบบจองรถ — “แบบไหนนับว่าจองชนกัน” — ทุกแถวกลายเป็นเคสทดสอบ 1 เคส

FR กับ NFR: NFR ต้องวัดได้

Functional (FR) — ระบบ “ทำอะไร”

“ระบบต้อง…” 1 ข้อต่อ 1 ความสามารถ เช่น ระบบต้องให้ admin เพิ่ม แก้ ลบข้อมูลรถ และทุกข้อต้องบอกที่มาได้ (ย่อหน้าในโจทย์ หรือคำตอบของเจ้าของโจทย์)

Non-functional (NFR) — ระบบ “ดีแค่ไหน”

ความปลอดภัย การใช้งาน ประสิทธิภาพ ค่าใช้จ่าย — ต้องมีเกณฑ์ตัวเลขหรือวิธีตรวจ ไม่อย่างนั้นจะตรวจรับไม่ได้

❌ NFR ที่ตรวจไม่ได้✅ NFR ที่วัดได้วิธีตรวจ
ใช้บนมือถือได้ใช้ทุกหน้าได้บนจอกว้าง 375px โดยไม่มี scroll แนวนอนสาธิต
ใช้งานง่ายผู้ใช้ที่เคยใช้แล้วทำรายการหลักเสร็จภายใน 1 นาทีสาธิต + จับเวลา
ปลอดภัยรหัสผ่านเก็บเป็น hash + salt (แปลงเป็นรหัสที่ย้อนกลับไม่ได้) ไม่มีรหัสจริงในฐานข้อมูลตรวจข้อมูล (inspection)
ประหยัดใช้เฉพาะบริการฟรีที่ไม่ต้องผูกบัตรตรวจหน้าจัดการบัญชี (dashboard)

requirement ที่ดี และแบบฝึกหาคำกำกวม

คุณสมบัติของ requirement ที่ดี (แนวคิดจากมาตรฐาน IEEE 29148):

คุณสมบัติถามตัวเอง
ไม่กำกวม (unambiguous)คนสองคนอ่านแล้วเข้าใจตรงกันไหม
ตรวจสอบได้ (verifiable)บอกได้ไหมว่าทำแล้วหรือยัง ด้วยวิธีไหน
ครบ (complete)กรณีผิดปกติ ข้อมูลที่ต้องกรอก สิทธิ์ ครบไหม
ไม่ขัดกันเอง (consistent)มีสองข้อที่ทำพร้อมกันไม่ได้ไหม
ตามรอยได้ (traceable)บอกได้ไหมว่ามาจากใคร/ย่อหน้าไหน และไปจบที่ test ไหน
🎯 แบบฝึก 3 นาที: หาคำกำกวม

แต่ละประโยค มีคำไหนที่ต้องถามต่อ? ถามว่าอะไร? (ตอบกับเพื่อนข้าง ๆ)

  1. “พนักงานต้องจองล่วงหน้าได้”
  2. “ระบบต้องห้ามจองชนกัน”
  3. “ยกเลิกได้ถ้าไม่ได้ไปแล้ว”
  4. “หน้าเว็บต้องโหลดเร็ว”
  5. “ผู้ดูแลจัดการข้อมูลได้”

ใบ้: แต่ละคำต้องถามต่ออย่างน้อย 1 ข้อ เช่น “ล่วงหน้า” ต้องถามว่า ล่วงหน้ากี่วัน? จองย้อนหลังได้ไหม? ส่วน “ผู้ดูแล” ต้องถามว่า คือใคร? จัดการอะไรได้บ้าง? — คำตอบจริงต้องได้จากเจ้าของโจทย์ใน Lab 2

Verification กับ Validation · วิธีตรวจ 4 แบบ

Verification — “สร้างถูกวิธีไหม”

เช็กว่าระบบทำได้ตรงกับ spec หรือไม่ ตรวจด้วย smoke test, trace และเช็กลิสต์ ช่วงบ่ายจะทำทุกครั้งที่จบแต่ละงานย่อย (task)

Validation — “สร้างของที่ถูกไหม”

เช็กว่า spec ตรงกับความต้องการจริงหรือไม่ ตรวจด้วยการถามเจ้าของโจทย์ (Lab 2) และให้ผู้ใช้ลองใช้เทียบกับโจทย์ต้นฉบับ (Lab 4)

📖 แนวคิดหลัก

ระบบที่ผ่าน test ครบ 100% ก็ยังใช้งานจริงไม่ได้ ถ้า spec ผิดตั้งแต่ต้น — test ตรวจได้แค่ว่าโค้ดตรงกับ spec spec ที่ดีจึงต้องผ่านการตรวจทั้งสองแบบ: เอาไปถามคนให้ยืนยันว่าถูกเรื่อง (validate) และเขียนให้ทุกข้อมีวิธีตรวจ (verify ได้)

ไม่ใช่ทุก requirement ที่ตรวจด้วย test อัตโนมัติได้ แต่ทุกข้อต้องมีวิธีตรวจ:

วิธีใช้เมื่อตัวอย่างวันนี้
Test ทดสอบผลเป็นข้อมูลที่เช็กอัตโนมัติได้smoke test: จองชน → 409
Demonstration สาธิตต้องดูด้วยตาหรือจับเวลาใช้บนมือถือ 375px · จองใน 1 นาที
Inspection ตรวจดูโค้ด/ข้อมูล/การตั้งค่าเปิดตาราง users เห็นแต่ hash
Analysis วิเคราะห์ต้องคำนวณหรือให้เหตุผลแพ็กเกจฟรี (free plan) รองรับปริมาณการใช้ได้ไหม

จัดลำดับด้วย MoSCoW และตามรอย (traceability)

ความต้องการมักมากกว่าเวลาที่มีเสมอ ใช้ MoSCoW แบ่ง: Must ต้องมี (Release 1) · Should ควรมี · Could อาจทำ · Won't ยังไม่ทำรอบนี้ — การเขียน “ยังไม่ทำ” ไว้ชัด ๆ สำคัญพอ ๆ กับสิ่งที่ทำ เพราะช่วยกันไม่ให้ agent (AI ที่ลงมือเขียนโค้ดให้) และทีม ทำงานเกินขอบเขต

npm run trace ตรวจความเชื่อมโยงนี้ให้อัตโนมัติ 3 เรื่อง: (1) AC ทุกข้อมีเคสทดสอบไหม (2) มีเคสไหนอ้างถึง AC ที่ไม่มีอยู่จริง (3) มี FR ไหนใน SRS ที่ไม่ถูกอ้างถึงใน SPEC เลย ซึ่งแปลว่าตกหล่น หรือลืมเขียนว่าเลื่อนไปรอบหน้า

Design: ข้อจำกัด → ภาพรวมระบบ → ADR → ข้อมูล → API

  1. ข้อจำกัด (constraint) ก่อน — สิ่งที่เราเลือกไม่ได้ เช่น ไม่มีงบ ไม่ผูกบัตร ต้องเสร็จใน 1 วัน มีระบบผู้ใช้จาก starter แล้ว
  2. สถาปัตยกรรม (ภาพรวมว่าระบบมีส่วนไหนบ้างและเชื่อมกันอย่างไร) — วาดแค่กล่องกับลูกศรก็พอ: 
    [เบราว์เซอร์บนมือถือ] ──HTTPS──▶ [Cloudflare Worker: public/ + Hono API src/] ──▶ [D1: app-db]
  3. ADR (Architecture Decision Record = บันทึกการตัดสินใจเรื่องโครงสร้างระบบ) — การตัดสินใจสำคัญ 1 ข้อเขียนเป็น 1 ADR มีหัวข้อ บริบท · ตัวเลือก · ตัดสินใจ · เหตุผล · ผลที่ตามมา เช่น “จะ deploy ที่ไหน: Cloudflare Workers + D1 เทียบกับเช่าเซิร์ฟเวอร์ (VPS) และ Google Sheets” — ส่วน “ทางเลือกที่ไม่ได้เลือก และเพราะอะไร” มีประโยชน์ที่สุดเมื่อกลับมาอ่านภายหลัง
  4. ข้อมูล — หาสิ่งที่ต้องเก็บ (entity) จากคำนามใน use case เช่น รถ, การจอง, ผู้ใช้ จากนั้นดูความสัมพันธ์ (ผู้ใช้ 1 คนมีหลายการจอง) แล้วออกแบบเป็นตารางพร้อมกฎของข้อมูล (ทะเบียนห้ามซ้ำ, เวลาเริ่มต้องก่อนเวลาจบ)
  5. API contract (ข้อตกลงว่า API แต่ละตัวรับและส่งอะไร) — หาจากคำกริยาใน use case แล้วระบุ method, path, ใครมีสิทธิ์เรียก, body, ผลเมื่อสำเร็จ และ error แต่ละแบบ
  6. NFR กับ design — ระบุว่าแต่ละ NFR แก้ด้วยการออกแบบอะไร เช่น “เห็นการจองของคนอื่นไม่ได้” แก้โดยให้ทุกคำสั่งดึงข้อมูล (query) กรองด้วย user_id ของคนที่ล็อกอินอยู่ (จาก session)
🪙 SRS กับ SPEC ต่างกันอย่างไร

docs/SRS.md และ docs/DESIGN.md คือฉบับเต็มสำหรับคนอ่าน ส่วน SPEC.md คือฉบับย่อสำหรับ agent (มีแค่ AC + data model + API) agent ต้องอ่าน SPEC.md ทุกครั้งที่เริ่มงานย่อย ยิ่งสั้นและชัดก็ยิ่งประหยัด token (หน่วยนับข้อความที่ AI อ่าน/เขียน ซึ่งกินโควตา)
