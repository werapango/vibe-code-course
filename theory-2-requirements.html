Stakeholder และการถามก่อนเขียน (elicitation)

Stakeholder คือทุกคนที่ได้รับผลจากระบบ — ไม่ใช่แค่คนกดใช้ เช่น ระบบจองรถ: เจ้าของโจทย์ (หัวหน้างาน), คนดูแลข้อมูล, พนักงานผู้จอง, และฝ่ายที่ “ไม่ได้ใช้แต่ได้รับผล” อย่างฝ่ายการเงินที่บอกว่าไม่มีงบ

Elicitation = การดึงความต้องการออกมาจากคน ไม่ใช่การเดา โจทย์จากผู้ใช้จริงมักกำกวมเสมอ เพราะผู้ใช้เขียนด้วยภาษาของงาน ไม่ใช่ภาษาของระบบ

⚠ กับดักของ LLM

ถ้าแปะโจทย์ให้ Gemini/ChatGPT แล้วสั่ง “เขียน SRS ให้หน่อย” มันจะเขียนออกมาสวยและมั่นใจมาก — รวมถึงกติกาที่ไม่มีใครเคยพูด (เช่น จองได้ไม่เกิน 4 ชั่วโมง, ต้องได้รับอนุมัติ) วิธีที่ถูกคือ: ให้ LLM ตั้งคำถามก่อน → คนเลือกคำถามไปถามเจ้าของโจทย์ → แล้วค่อยให้ช่วยเขียน ข้อไหนยังไม่มีคนยืนยัน ให้ติดป้าย [สมมติฐาน]

Use case และ user story

Use case — มองเป็น “การใช้งานหนึ่งเรื่อง”

เริ่มจากรายการ use case (UC-01, UC-02 …) แล้วเขียน use case หลัก 1 ตัวแบบเต็ม (fully dressed) ตัวอย่างโครงจาก SRS อ้างอิง:

UC-02 จองรถ
Actor: พนักงาน
เงื่อนไขก่อนเริ่ม: ล็อกอินแล้ว · มีรถในระบบอย่างน้อย 1 คัน
ขั้นตอนหลัก:
  1. เลือกรถ และดูตารางของรถคันนั้นในวันที่ต้องการ
  2. กรอกรายละเอียดการจอง
  3. ระบบตรวจกติกา
  4. ระบบบันทึก และแสดงใน "การจองของฉัน"
ทางเลือก / กรณีผิดปกติ:
  3a. ถ้า ... ระบบปฏิเสธพร้อมแจ้งเหตุผล → กลับไปขั้น 1
ผลลัพธ์: การจองถูกบันทึก ช่วงเวลานั้นแสดงว่า "ไม่ว่าง"

ส่วน ทางเลือก/กรณีผิดปกติ คือขุมทรัพย์ — แต่ละข้อมักกลายเป็น requirement และเคสทดสอบ ส่วน “กรอกรายละเอียดอะไรบ้าง” และ “กติกาอะไร” คุณต้องไปถามเองใน Lab 2

User story — มองจากคุณค่าที่ผู้ใช้ได้

รูปแบบ: ในฐานะ [ใคร] ฉันต้องการ [ทำอะไร] เพื่อ [ได้ประโยชน์อะไร] · story ที่ดีผ่านเกณฑ์ INVEST:

ตัวอักษรความหมายถามตัวเอง
Independentอิสระทำเรื่องนี้ได้โดยไม่ต้องรอเรื่องอื่นมากไหม
Negotiableต่อรองได้บอก “อะไร” ไม่ล็อก “วิธี” จนแก้ไม่ได้
Valuableมีคุณค่าส่วน “เพื่อ…” ชัดไหม ใครได้ประโยชน์
Estimableประเมินได้รู้พอจะบอกได้ไหมว่าใหญ่แค่ไหน
Smallเล็กพอเสร็จได้ในรอบเดียว
Testableทดสอบได้มี acceptance criteria ที่บอกผ่าน/ไม่ผ่านได้ชัด

Acceptance criteria และ Specification by Example

AC เขียนแบบ Given / When / Then — สถานะก่อน · การกระทำ · ผลที่ตรวจได้ ตัวอย่างจริงจาก starter:

- **AC-A2.2** Given รหัสผิด หรือไม่มีชื่อนี้ When ล็อกอิน
  Then ได้ 401 ด้วยข้อความเดียวกันทั้งสองกรณี

รหัส AC ตัวหนา **AC-x.y** จะกลายเป็นชื่อเคสใน scripts/smoke.mjs และ npm run trace ตรวจว่า AC ทุกข้อมีเคสทดสอบ

Specification by Example: เขียน “ผลที่คาดหวัง” ก่อนโค้ด

กติกาที่มีหลายกรณี เขียนเป็นประโยคเดียวจะกำกวม ให้เขียนเป็นตารางตัวอย่าง แล้วเติมผลที่คาดหวังเองก่อนให้ใครเขียนโค้ด เช่น กติกา “ชื่อผู้ใช้”:

#ชื่อผู้ใช้ที่กรอกผลที่คาดหวังเหตุผล
1somchai_01รับa-z 0-9 _ ยาว 3–30
2ab400สั้นกว่า 3
3สมชาย400ไม่ใช่ a-z
4ชื่อที่มีอยู่แล้ว409ซ้ำ

ใน Lab 2 คุณจะทำตารางแบบนี้กับกติกาที่ยากที่สุดของระบบจองรถ — “แบบไหนนับว่าจองชนกัน” — ทุกแถวกลายเป็นเคสทดสอบ 1 เคส

FR กับ NFR: NFR ต้องวัดได้

Functional (FR) — ระบบ “ทำอะไร”

“ระบบต้อง…” 1 ข้อ = 1 ความสามารถ เช่น ระบบต้องให้ admin เพิ่ม แก้ ลบข้อมูลรถ · ทุกข้อมีที่มา (ย่อหน้าในโจทย์ หรือคำตอบของเจ้าของโจทย์)

Non-functional (NFR) — ระบบ “ดีแค่ไหน”

ความปลอดภัย การใช้งาน ประสิทธิภาพ ค่าใช้จ่าย — ต้องมีเกณฑ์ตัวเลขหรือวิธีตรวจ ไม่งั้นตรวจรับไม่ได้

❌ NFR ที่ตรวจไม่ได้✅ NFR ที่วัดได้วิธีตรวจ
ใช้บนมือถือได้ใช้ทุกหน้าได้บนจอกว้าง 375px โดยไม่มี scroll แนวนอนสาธิต
ใช้งานง่ายผู้ใช้ที่เคยใช้แล้วทำรายการหลักเสร็จภายใน 1 นาทีสาธิต + จับเวลา
ปลอดภัยรหัสผ่านเก็บเป็น hash + salt ไม่มีรหัสจริงในฐานข้อมูลตรวจข้อมูล (inspection)
ประหยัดใช้เฉพาะบริการฟรีที่ไม่ต้องผูกบัตรตรวจ dashboard

requirement ที่ดี + แบบฝึกล่าคำกำกวม

คุณสมบัติของ requirement ที่ดี (แนวคิดจากมาตรฐาน IEEE 29148):

คุณสมบัติถามตัวเอง
ไม่กำกวม (unambiguous)คนสองคนอ่านแล้วเข้าใจตรงกันไหม
ตรวจสอบได้ (verifiable)บอกได้ไหมว่าทำแล้วหรือยัง ด้วยวิธีไหน
ครบ (complete)กรณีผิดปกติ ข้อมูลที่ต้องกรอก สิทธิ์ ครบไหม
ไม่ขัดกันเอง (consistent)มีสองข้อที่ทำพร้อมกันไม่ได้ไหม
ตามรอยได้ (traceable)บอกได้ไหมว่ามาจากใคร/ย่อหน้าไหน และไปจบที่ test ไหน
🎯 แบบฝึก 3 นาที: ล่าคำกำกวม

แต่ละประโยค มีคำไหนที่ต้องถามต่อ? ถามว่าอะไร? (ตอบกับเพื่อนข้าง ๆ)

  1. “พนักงานต้องจองล่วงหน้าได้”
  2. “ระบบต้องห้ามจองชนกัน”
  3. “ยกเลิกได้ถ้าไม่ได้ไปแล้ว”
  4. “หน้าเว็บต้องโหลดเร็ว”
  5. “ผู้ดูแลจัดการข้อมูลได้”

ใบ้: แต่ละคำซ่อนคำถามอย่างน้อย 1 ข้อ เช่น “ล่วงหน้า” → กี่วัน? ย้อนหลังได้ไหม? · “ผู้ดูแล” → ใคร? จัดการอะไรได้บ้าง? — คำตอบจริงต้องได้จากเจ้าของโจทย์ใน Lab 2

Verification กับ Validation · วิธีตรวจ 4 แบบ

Verification — “สร้างถูกวิธีไหม”

ระบบตรงกับ spec หรือไม่ · ตรวจด้วย smoke test, trace, เช็กลิสต์ · ทำทุก task ในช่วงบ่าย

Validation — “สร้างของที่ถูกไหม”

spec ตรงกับความต้องการจริงหรือไม่ · ตรวจด้วยการถามเจ้าของโจทย์ (Lab 2) และตรวจรับกับผู้ใช้เทียบโจทย์ต้นฉบับ (Lab 4)

📖 แนวคิดหลัก

ระบบที่ผ่าน test ครบ 100% ก็ยังล้มได้ ถ้า spec ผิดตั้งแต่ต้น — test ตรวจได้แค่ว่าโค้ดตรงกับ spec spec ที่ดีจึงต้องผ่านทั้งสองทาง: validate กับคน (ถูกเรื่องไหม) และเขียนให้ verify ได้ (ทุกข้อมีวิธีตรวจ)

ไม่ใช่ทุก requirement ที่ตรวจด้วย test อัตโนมัติได้ แต่ทุกข้อต้องมีวิธีตรวจ:

วิธีใช้เมื่อตัวอย่างวันนี้
Test ทดสอบผลเป็นข้อมูลที่เช็กอัตโนมัติได้smoke test: จองชน → 409
Demonstration สาธิตต้องดูด้วยตาหรือจับเวลาใช้บนมือถือ 375px · จองใน 1 นาที
Inspection ตรวจดูโค้ด/ข้อมูล/การตั้งค่าเปิดตาราง users เห็นแต่ hash
Analysis วิเคราะห์ต้องคำนวณหรือให้เหตุผลfree plan รองรับปริมาณการใช้ได้ไหม

จัดลำดับด้วย MoSCoW และตามรอย (traceability)

ความต้องการมักมากกว่าเวลาที่มีเสมอ ใช้ MoSCoW แบ่ง: Must ต้องมี (Release 1) · Should ควรมี · Could อาจทำ · Won't ยังไม่ทำรอบนี้ — การเขียน “ยังไม่ทำ” ไว้ชัด ๆ สำคัญพอ ๆ กับสิ่งที่ทำ เพราะกัน agent (และทีม) ทำเกิน

Design: constraint → สถาปัตยกรรม → ADR → ข้อมูล → API

  1. Constraint ก่อน — ข้อจำกัดที่เลือกไม่ได้ เช่น ไม่มีงบ ไม่ผูกบัตร ต้องเสร็จใน 1 วัน มีระบบผู้ใช้จาก starter แล้ว
  2. สถาปัตยกรรม — กล่องกับลูกศรพอ: 
    [เบราว์เซอร์บนมือถือ] ──HTTPS──▶ [Cloudflare Worker: public/ + Hono API src/] ──▶ [D1: app-db]
  3. ADR (Architecture Decision Record) — การตัดสินใจสำคัญ 1 ข้อ = 1 ADR: บริบท · ตัวเลือก · ตัดสินใจ · เหตุผล · ผลที่ตามมา เช่น “ที่ deploy: Cloudflare Workers + D1 เทียบกับ VPS และ Google Sheets” — ส่วน “ทางเลือกที่ไม่เลือก” คือส่วนที่มีค่าที่สุดเวลาย้อนกลับมาอ่าน
  4. ข้อมูล — หา entity จากคำนามใน use case (รถ, การจอง, ผู้ใช้) → ความสัมพันธ์ (ผู้ใช้ 1 คนมีหลายการจอง) → ตาราง + constraint (ทะเบียนห้ามซ้ำ, เวลาเริ่มก่อนเวลาจบ)
  5. API contract — หาจากคำกริยาใน use case: method, path, สิทธิ์, body, ผลสำเร็จ, error แต่ละแบบ
  6. NFR → design — แต่ละ NFR แก้ด้วยอะไร เช่น “เห็นการจองของคนอื่นไม่ได้” → ทุก query กรอง user_id จาก session
🪙 SRS กับ SPEC ต่างกันอย่างไร

docs/SRS.md + docs/DESIGN.md = ฉบับเต็มสำหรับคน · SPEC.md = ฉบับย่อสำหรับ agent (AC + data model + API) agent อ่าน SPEC.md ทุก task — ยิ่งสั้นและชัด ยิ่งประหยัด token

คำถามชวนคุย

  1. ถ้า LLM เขียน requirement ที่ “ฟังดูดี” แต่เจ้าของโจทย์ไม่เคยพูด แล้วเราสร้างตามนั้น — ผิดที่ใคร? ป้องกันอย่างไร?
  2. requirement ข้อไหนของระบบที่คุณเคยใช้ ที่ตรวจด้วย test อัตโนมัติไม่ได้ แล้วควรตรวจด้วยวิธีไหน?
  3. ทำไมการเขียน “ยังไม่ทำ (Won't)” ไว้ใน spec ถึงช่วยประหยัด token?
