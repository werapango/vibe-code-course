1 · เช็กลิสต์ verification บน production (10 นาที)

🎯 เจตนา

smoke test ตรวจ AC ให้แล้ว แต่บางเรื่องตรวจด้วยวิธีอื่น: ตรวจ (inspection) ข้อมูลในฐานข้อมูล · สาธิต (demonstration) บนมือถือ — ทำบน production ซึ่งเป็นของที่ผู้ใช้จะใช้จริง

#ตรวจอะไรวิธีตรวจวิธีผล
1ไม่ล็อกอิน เรียกการจองไม่ได้เปิดหน้าต่าง InPrivate แล้วไปที่ https://…workers.dev/api/bookings ต้องเห็น {"error":"กรุณาเข้าสู่ระบบ"} (401)test☐

2 · ตรวจรับกับ "ผู้ใช้" (10 นาที)

🎯 เจตนา

ทุก test ผ่าน ≠ ผู้ใช้พอใจ · ให้เพื่อนเล่นบท หัวหน้างานยานพาหนะ ใช้ระบบของคุณบนมือถือ แล้วตรวจเทียบกับ โจทย์ต้นฉบับ B1–B7 — ไม่ใช่เทียบกับ SPEC เพราะ spec เองก็อาจผิดหรือขาดได้

  1. จับคู่ คนหนึ่งเป็น "ผู้ใช้" อีกคนเป็นทีมพัฒนา (สลับกันหลัง 5 นาที)
  2. "ผู้ใช้" อ่านโจทย์ทีละย่อหน้า แล้วลองทำสิ่งนั้นในระบบจริง
  3. ทีมพัฒนาจดผลลงตาราง ห้ามอธิบายแก้ตัว — จดอย่างเดียว
ย่อหน้า"ผู้ใช้" ลองอะไรผลถ้าไม่ตรง: เป็นแบบไหน
B2จองรถคันเล็กไป 5 คน☐ ตรง ☐ ไม่ตรง
B3ดูว่ารถว่างไหม · จองชน · ยกเลิก☐ ตรง ☐ ไม่ตรง
B4เพิ่มรถใหม่ · สร้างบัญชีพนักงาน☐ ตรง ☐ ไม่ตรง
B5ยกเลิกการจองของคนอื่น☐ ตรง ☐ ไม่ตรง
B6จองล่วงหน้า · ขออนุมัติ☐ ตรง ☐ ไม่ตรง
B1, B7ใช้แทน LINE/สมุดได้จริงไหม · มีค่าใช้จ่ายไหม☐ ตรง ☐ ไม่ตรง

🐞 bug

ระบบไม่ตรงกับ spec — เช่น AC บอกต่อคิวพอดีได้ แต่ระบบปฏิเสธ · แก้ที่โค้ด แล้วเพิ่มเคส smoke ที่จับได้

🕳 requirement gap

ระบบตรง spec แต่ spec ไม่ครอบคลุมความต้องการ — แก้ที่ spec ก่อน (SRS → AC → task) แล้วค่อยโค้ด

📌 ตั้งใจเลื่อน

อยู่ใน SRS แต่จัดเป็น Release 2 หรือ "ยังไม่ทำ" — เช่น B6 การอนุมัติ → FR-14 · ตอบผู้ใช้ได้ว่า "อยู่ในแผน รอบหน้า" เพราะเขียนไว้แล้ว

📖 ข้อสังเกต

ถ้าตอนเช้าไม่ได้ถามเจ้าของโจทย์เรื่องการอนุมัติ (Q3) ช่องนี้จะกลายเป็น "requirement gap" ที่น่าอายต่อหน้าผู้ใช้ — การบันทึกสิ่งที่ตั้งใจไม่ทำไว้ใน spec จึงสำคัญพอ ๆ กับสิ่งที่ทำ

3 · กลุ่มเร็ว: เลือก 1 อย่าง

ก. Change request: FR-11 หรือ FR-12

🎯 เจตนา

เจ้าของโจทย์ขอเพิ่มหลังเห็นระบบ — ฝึกเดินวงจรครบ SRS → SPEC (AC + ตัวอย่าง) → smoke → TASKS → agent → verify โดยไม่ข้ามขั้น

  1. เลือก FR-11 (จองล่วงหน้าไม่เกิน 30 วัน) หรือ FR-12 (ยกเลิกได้เฉพาะก่อนเวลาเริ่ม) — ย้ายจาก §7 ใน SPEC.md มาเป็น US/AC ใหม่ เช่น **AC-2.8** พร้อมแถวตัวอย่างขอบเขต (วันที่ 30 ได้ · วันที่ 31 ไม่ได้)
  2. รัน npm run trace → ต้องเห็น ❌ AC ใหม่ยังไม่มีเคส (ดีแล้ว: spec นำหน้าโค้ด)
  3. เพิ่ม task ใน TASKS.md เช่น T3.1 แล้วสั่ง ทำ task T3.1 ใน TASKS.md
  4. smoke + trace ✅ → commit → migration (ถ้ามี) → deploy

ข้อสังเกตสำหรับ FR-12: เคส "ยกเลิกหลังเวลาเริ่มไม่ได้" เขียนเป็น smoke test ยาก (สร้างการจองในอดีตไม่ได้เพราะ AC-2.5) — ตัดสินใจว่าจะตรวจด้วยวิธีไหน แล้วเขียนวิธีตรวจลงใน SPEC

ข. ล่าบั๊กปลูก

ขอการ์ดบั๊กจากผู้สอน ติดตั้งตามการ์ด แล้วหาว่า smoke test เคสไหนจับได้ — มีบั๊กหนึ่งตัวที่ smoke test จับไม่ได้ ต้องใช้วิธีตรวจอื่น ลองหาให้เจอ

5 · คำถาม retro (ช่วง 15:45)

  1. วางแต่ละ commit ของคุณวันนี้ลงบน phase ของ SDLC — phase ไหนที่ AI ช่วยมากที่สุด และ phase ไหนที่คนต้องทำเองทั้งหมด?
  2. คำถามข้อไหนที่ถามเจ้าของโจทย์ตอนเช้า ถ้าไม่ได้ถาม ระบบจะสร้างผิด?
  3. SRS ตอนเช้าของคุณ "แต่งเพิ่ม" (⚠) กี่ข้อ — LLM เดาอะไรที่ไม่มีในโจทย์?
  4. มีอะไรที่ smoke test ผ่านหมดแต่ผู้ใช้ยังไม่พอใจไหม? เป็น bug หรือ gap?
  5. ถ้าต้องสร้างระบบใหม่พรุ่งนี้ (เช่น จองห้องประชุม) จะใช้อะไรจากวันนี้ซ้ำได้บ้าง? (starter, template, skill, STARTER-PROMPT)
