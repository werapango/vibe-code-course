2 · ตรวจรับกับ "ผู้ใช้" (8 นาที)

🎯 ทำขั้นนี้เพื่ออะไร

ผ่านทุก test ไม่ได้แปลว่าผู้ใช้จะพอใจ ให้เพื่อนเล่นบท หัวหน้างานยานพาหนะ ลองใช้ระบบของคุณบนมือถือ แล้วตรวจเทียบกับ โจทย์ต้นฉบับ ย่อหน้า B1–B7 ไม่ใช่เทียบกับ SPEC เพราะ spec เองก็อาจเขียนผิดหรือตกหล่นได้

  1. จับคู่ คนหนึ่งเป็น "ผู้ใช้" อีกคนเป็นทีมพัฒนา (สลับกันหลัง 4 นาที)
  2. "ผู้ใช้" อ่านโจทย์ทีละย่อหน้า แล้วลองทำสิ่งนั้นในระบบจริง
  3. ทีมพัฒนาจดผลลงตารางด้านล่าง ห้ามอธิบายหรือโต้แย้ง ให้จดอย่างเดียว ถ้าไม่ตรง ให้ระบุว่าเป็นแบบไหนใน 3 แบบใต้ตาราง

🐞 bug

ระบบไม่ตรงกับ spec เช่น AC บอกว่าจองต่อคิวพอดีได้ แต่ระบบปฏิเสธ วิธีแก้คือแก้โค้ด แล้วเพิ่มเคส smoke ที่จับบั๊กนี้ได้

🕳 requirement gap (ความต้องการตกหล่น)

ระบบตรง spec แต่ spec ไม่ครอบคลุมสิ่งที่ผู้ใช้ต้องการ วิธีแก้คือแก้ spec ก่อน (SRS แล้ว AC แล้ว task) แล้วค่อยแก้โค้ด

📌 ตั้งใจเลื่อน

มีเขียนไว้ใน SRS แต่จัดไว้ใน Release 2 หรือ "ยังไม่ทำ" เช่น เรื่องการอนุมัติใน B6 ถูกบันทึกเป็น FR-14 จึงตอบผู้ใช้ได้ว่า "อยู่ในแผนรอบหน้า" เพราะเขียนไว้แล้ว

📖 ข้อสังเกต

ถ้าตอนเช้าไม่ได้ถามเจ้าของโจทย์เรื่องการอนุมัติ (คำถาม Q3) เรื่องนี้จะกลายเป็น "requirement gap" ที่ผู้ใช้มาพบตอนตรวจรับ ดังนั้นการบันทึกสิ่งที่ตั้งใจไม่ทำไว้ใน spec จึงสำคัญพอ ๆ กับสิ่งที่ทำ

3 · ปิด release v1.0

🎯 ทำขั้นนี้เพื่ออะไร

ติดป้ายชื่อเวอร์ชัน (tag) ให้ commit ที่ผ่านการตรวจรับแล้ว วันหน้าจะย้อนกลับมาดูได้ว่า "เวอร์ชันที่ผู้ใช้รับไป" คือโค้ดชุดไหน

รันใน Git Bash ทีละคำสั่ง คำสั่งสุดท้ายต้องเห็นคำว่า tag: v1.0 ที่ commit บนสุด

git add . && git commit -m "release 1: verified and accepted"
git tag v1.0
git log --oneline --decorate
✅ ผ่าน Lab 4 เมื่อ
  • เช็กลิสต์ verification ผ่านครบ 7 ข้อบน production
  • ตารางตรวจรับมีผลครบทุกย่อหน้า และแยก bug / gap / ตั้งใจเลื่อน ได้
  • มี tag v1.0 ใน git log
  • deploy v1.1 ด้วย agent สำเร็จ (ข้อ 4) และบอกได้ว่า agent รันคำสั่งอะไรไปบ้าง

4 · ลอง deploy ด้วย agent (10 นาที)

🎯 ทำขั้นนี้เพื่ออะไร

ทั้งวันคุณพิมพ์คำสั่ง Cloudflare เองจนรู้แล้วว่าแต่ละคำสั่งทำอะไร ข้อนี้ลองให้ agent ทำแทนดูบ้าง โดยใช้ Cloudflare agent setup ซึ่งเป็นชุดคำสั่งที่ Cloudflare เตรียมไว้ให้ agent ติดตั้งความรู้เรื่อง Cloudflare (skills) และเชื่อมกับบัญชี Cloudflare ของคุณเอง (MCP) จะได้เห็นว่า agent ทำได้เร็วแค่ไหน และต้องได้สิทธิ์อะไรบ้างจึงทำได้

1

จดโควต้าก่อนเริ่ม

เปิดหน้า Usage Stats ใน ZCode แล้วจดตัวเลขโควต้าที่เหลือไว้ (จะเทียบหลังจบข้อนี้)

2

ให้ agent ตั้งค่า Cloudflare เอง

ใน ZCode กด New task ในโปรเจกต์ my-app ตรวจว่าโหมดเป็น Ask before changes (ไอคอนมือ ✋) แล้วพิมพ์:

Fetch and execute the appropriate instructions to set me up for Cloudflare from https://developers.cloudflare.com/agent-setup/prompt.md
  • ZCode จะขออนุญาตรันคำสั่งทีละข้อ เช่น npx -y skills add cloudflare/skills … อ่านทุกคำสั่งก่อนกด Allow ถ้าไม่เข้าใจว่าคำสั่งทำอะไร ให้กด Reject แล้วถาม agent ก่อน
  • ถ้าถามว่าจะติดตั้ง cf CLI ไหม ให้ตอบไม่ติดตั้ง (วันนี้ใช้ wrangler อยู่แล้ว)
  • ถ้าเบราว์เซอร์เปิดหน้า Cloudflare ให้อนุญาต ตรวจว่าเป็นอีเมลของคุณก่อนกดยืนยัน — ขั้นนี้คือการให้ agent เข้าถึงบัญชีของคุณ
3

สั่งให้ agent แก้และ deploy เวอร์ชัน 1.1

AGENTS.md ของ starter ห้าม agent รันคำสั่ง wrangler ไว้ จึงต้องบอกข้อยกเว้นให้ชัดในคำสั่ง (นี่คือการปรับกติกาของ agent อย่างตั้งใจ ตรงกับขั้น Improve ของ ADLC ในทฤษฎี 3):

ครั้งนี้ผู้สอนอนุญาตให้คุณรันคำสั่ง deploy เองได้ เป็นข้อยกเว้นจากกติกาใน AGENTS.md เฉพาะงานนี้เท่านั้น
งาน: แก้หัวข้อของหน้าแรกให้มีคำว่า "v1.1" แล้ว deploy my-app ขึ้น Cloudflare
ห้ามรัน migration ห้ามลบ Worker หรือฐานข้อมูล และบอกทุกคำสั่งที่จะรันก่อนรัน

อ่านคำสั่ง deploy ที่ agent ขอรันก่อนกด Allow (ห้ามกด Always Allow)

4

ตรวจผลด้วยตัวเอง แล้ว commit

เปิด URL ของแอปแล้วรีเฟรช ต้องเห็น "v1.1" จากนั้นพิมพ์ใน Git Bash เพื่อยืนยันว่ามี deployment ใหม่อยู่บนสุด แล้ว commit การแก้ของ agent:

npx wrangler deployments list
git add . && git commit -m "v1.1: deployed by agent"

สุดท้ายเปิด Usage Stats อีกครั้ง แล้วเทียบกับตัวเลขที่จดไว้ในขั้นที่ 1

⚠ ถ้า agent deploy แล้วหน้าเว็บพัง

คุณย้อนกลับเองได้ทันทีด้วย npx wrangler rollback ใน Git Bash (แบบเดียวกับที่ทำใน Lab 1) ไม่ต้องรอ agent

📖 คิดก่อนใช้ในงานจริง

agent deploy ได้เร็วกว่าพิมพ์เอง แต่ถ้า deploy ผิด คนที่กด Allow ยังเป็นคนรับผิดชอบ และถ้าไม่เคยพิมพ์คำสั่งเหล่านี้เองมาก่อน ก็จะตัดสินไม่ได้ว่าคำสั่งที่ agent ขอรันนั้นปลอดภัยหรือไม่ นี่คือเหตุผลที่วันนี้ให้พิมพ์เองก่อน แล้วค่อยลองให้ agent ทำตอนท้าย

5 · ถ้ายังมีเวลา: เลือก 1 อย่าง

ทำหลังข้อ 4 เสร็จแล้วเท่านั้น ถ้าเวลาหมดให้ข้ามไปข้อ 6

ก. Change request (คำขอเปลี่ยน): FR-11 หรือ FR-12

🎯 ทำขั้นนี้เพื่ออะไร

สมมติว่าเจ้าของโจทย์เห็นระบบแล้วขอเพิ่มความสามารถ ให้ฝึกทำครบทุกขั้นตามลำดับโดยไม่ข้าม: แก้ SRS ก่อน แล้วเขียน AC และตัวอย่างใน SPEC จากนั้นให้มีเคส smoke เพิ่ม task ใน TASKS แล้วจึงสั่ง agent และตรวจผล

  1. เลือก FR-11 (จองล่วงหน้าไม่เกิน 30 วัน) หรือ FR-12 (ยกเลิกได้เฉพาะก่อนเวลาเริ่ม) แล้วเปิด SPEC.md ย้ายข้อนั้นจาก §7 (นอกขอบเขต) มาเขียนเป็น user story และ AC ใหม่ เช่น **AC-2.8** พร้อมแถวตัวอย่างกรณีค่าขอบ (วันที่ 30 จองได้ · วันที่ 31 จองไม่ได้)
  2. รัน npm run trace ใน Git Bash ต้องเห็น ❌ ที่ AC ใหม่ เพราะยังไม่มีเคสทดสอบ (ถูกต้องแล้ว: เขียน spec ก่อนโค้ด)
  3. เพิ่ม task ใหม่ใน TASKS.md เช่น T3.1 แล้วพิมพ์ใน ZCode ว่า ทำ task T3.1 ใน TASKS.md
  4. รัน smoke และ trace จนเป็น ✅ แล้ว commit จากนั้นรัน migration แบบ --remote (ถ้ามีไฟล์ใหม่) แล้ว deploy

ข้อสังเกตสำหรับ FR-12: เคส "ยกเลิกหลังเวลาเริ่มไม่ได้" เขียนเป็น smoke test ยาก เพราะระบบไม่ยอมให้สร้างการจองในอดีต (AC-2.5) ให้ตัดสินใจว่าจะตรวจข้อนี้ด้วยวิธีไหน แล้วเขียนวิธีตรวจนั้นลงใน SPEC

ข. หาบั๊กที่ผู้สอนใส่ไว้

ขอการ์ดบั๊กจากผู้สอน แก้โค้ดตามการ์ดเพื่อใส่บั๊กเข้าไป แล้วหาว่า smoke test เคสไหนจับบั๊กนั้นได้ มีบั๊กหนึ่งตัวที่ smoke test จับไม่ได้ ต้องใช้วิธีตรวจอื่น ลองหาให้เจอ

retro (retrospective) คือการทบทวนว่าวันนี้อะไรได้ผล อะไรควรทำต่างไป ใช้คำถามเหล่านี้คุยกับคู่หรือในกลุ่ม

  1. ไล่ดู commit ของคุณวันนี้ (git log --oneline) แล้วจับคู่แต่ละ commit กับขั้นของ SDLC (เช่น Requirements, Design, Implementation, Testing, Deployment) ขั้นไหนที่ AI ช่วยมากที่สุด และขั้นไหนที่คนต้องทำเองทั้งหมด?
  2. คำถามข้อไหนที่ถามเจ้าของโจทย์ตอนเช้า ถ้าไม่ได้ถาม ระบบจะสร้างผิด?
  3. SRS ตอนเช้าของคุณมีข้อที่ AI "แต่งเพิ่ม" (ช่อง ⚠ ในตาราง 4 ช่องตอน Baseline) กี่ข้อ AI เดาอะไรที่ไม่มีในโจทย์บ้าง?
  4. มีอะไรที่ smoke test ผ่านหมดแต่ผู้ใช้ยังไม่พอใจไหม? เป็น bug หรือ gap?
  5. ตอนให้ agent deploy (ข้อ 4) มันรันคำสั่งอะไรบ้าง ใช้โควต้าไปเท่าไร และถ้าเป็นงานจริงของหน่วยงาน คุณจะยอมให้ agent deploy เองไหม ในกรณีไหน?
  6. ถ้าต้องสร้างระบบใหม่พรุ่งนี้ (เช่น จองห้องประชุม) จะใช้อะไรจากวันนี้ซ้ำได้บ้าง? (เช่น โปรเจกต์ตั้งต้น starter, แม่แบบเอกสาร template, skill และ prompt สร้าง starter ใน ข้อ 7)

แบบด่วน — prompt เดียว ให้ agent ทำเองจนจบ

ทำในโฟลเดอร์ว่าง บนเครื่องและบัญชี Cloudflare ของตัวเอง · รัน npx wrangler login ไว้ก่อน (ต้องล็อกอินผ่านเบราว์เซอร์ agent ทำแทนไม่ได้) · ใช้โหมด Ask before changes แล้วอ่านคำสั่งก่อนกด Allow ทุกครั้ง

สร้าง "starter" เว็บแอปบน Cloudflare ในโฟลเดอร์นี้ให้เสร็จจนใช้งานได้
คุณทำเองได้ทั้งหมด รวมถึงรันคำสั่ง npm, npx wrangler และ git — ยกเว้น ห้าม deploy ขึ้น production จนกว่าฉันจะสั่ง

สิ่งที่ต้องได้:
1. โปรเจกต์ Cloudflare Workers + Hono (TypeScript) + D1 (binding ชื่อ DB, ฐานข้อมูลชื่อ app-db) + Static Assets ในโฟลเดอร์ public/
   (สร้างด้วย npm create cloudflare@latest แบบไม่ deploy แล้วติดตั้ง hono)
2. GET /api/health ตอบ { ok, db, time } โดย db บอกสถานะ "ready" / "no-binding" / "not-migrated"
3. ระบบผู้ใช้: ตั้งค่าครั้งแรก (สร้าง admin คนแรกได้เฉพาะตอนยังไม่มีผู้ใช้), login, logout, me,
   เปลี่ยนรหัสของตัวเอง (ต้องยืนยันรหัสเดิม) และ admin จัดการผู้ใช้ (เพิ่ม แก้ ลบ ตั้งรหัสใหม่)
4. หน้าเว็บ HTML/CSS/JS ธรรมดา (ไม่ใช้ framework) ใช้บนมือถือได้: ตั้งค่าครั้งแรก, ล็อกอิน, หน้าหลัก, จัดการผู้ใช้, เปลี่ยนรหัส
5. scripts/smoke.mjs ทดสอบทุกกติกาโดยเรียก API จริง (รับ url= user= pass= ต่อท้ายคำสั่ง ชื่อเคสขึ้นต้นด้วยรหัส AC)
   และ scripts/trace.mjs ตรวจว่า AC ทุกข้อใน SPEC.md มีเคสทดสอบ · npm scripts: dev, deploy, smoke, trace
6. เอกสาร: AGENTS.md, SPEC.md (ส่วนผู้ใช้เขียนครบเป็นตัวอย่าง: user story + AC แบบ Given/When/Then มีรหัสตัวหนา),
   README.md และแม่แบบ docs/SRS.md, docs/DESIGN.md, TASKS.md

ข้อบังคับ (ห้ามละเว้น):
- ใช้เฉพาะบริการใน Cloudflare free plan ห้ามใช้บริการที่ต้องผูกบัตร (เช่น Access, R2, Email)
- รหัสผ่านเก็บแบบ hash: PBKDF2-SHA256 100,000 รอบ + salt สุ่ม · session token สุ่ม 32 ไบต์ อายุ 7 วัน ใน cookie HttpOnly + SameSite=Lax
- SQL ทุกคำสั่งเป็น prepared statement · เปลี่ยนโครงสร้างฐานข้อมูลด้วยไฟล์ migration เท่านั้น
- ตรวจสิทธิ์ที่ server ทุกคำขอ · ล็อกอินผิดตอบข้อความเดียวกันไม่ว่าชื่อหรือรหัสผิด
  admin ลบตัวเองไม่ได้ · ต้องเหลือ admin อย่างน้อย 1 คน · ตั้งรหัสใหม่ให้ใครแล้ว session เดิมของคนนั้นต้องใช้ไม่ได้
- คอมเมนต์และข้อความ error เป็นภาษาไทย · API ตอบ JSON { "error": "..." } พร้อม status ที่ถูกต้อง

ลำดับการทำ:
- สร้างฐานข้อมูลด้วย npx wrangler d1 create app-db --binding DB --update-config
  (ถ้ายังไม่ได้ล็อกอิน Cloudflare ให้หยุด แล้วบอกให้ฉันรัน npx wrangler login เอง)
- รัน migration แบบ --local เปิด npm run dev แล้วรัน npm run smoke จนผ่านทุกเคส และ npm run trace ขึ้นว่าครบ
- git commit เป็นช่วง ๆ ทุกครั้งที่ส่วนหนึ่งทำงานได้
- จบแล้วสรุปให้ฉัน: ไฟล์ที่สร้าง ผล smoke/trace และคำสั่งที่ฉันต้องรันเองเพื่อ deploy
⚠ ที่ยังห้ามไว้ และทำไม

แบบด่วนเอาข้อห้ามเรื่อง “agent ห้ามรันคำสั่ง” ออกเพื่อให้คนทำน้อยลง แต่ยังคง 4 เรื่องไว้เพราะถ้าเอาออกจะได้ระบบที่ใช้ไม่ได้หรือไม่ปลอดภัย: ใช้เฉพาะของฟรี · เก็บรหัสผ่านแบบ hash และใช้ prepared statement · ห้าม deploy จนกว่าจะสั่ง · ต้องมี smoke test ที่ผ่าน — และไม่ว่า agent จะรายงานว่าเสร็จแล้ว ให้รัน npm run smoke ด้วยตัวเองอีกครั้งก่อน deploy

แบบทีละ task — คนรันคำสั่งเอง ตรวจทุกขั้น

เขียนแบบ spec + WBS (WBS = แตกงานใหญ่เป็นงานย่อย): ส่งข้อมูลพื้นหลังของโปรเจกต์ (บริบท) ให้ AI ครั้งเดียว แล้วสั่งทีละงานย่อย (task) โดยคนเป็นผู้รันคำสั่งเอง และตรวจด้วย smoke/trace หลังจบทุก task

ส่วนที่ 1 — บริบท (ข้อมูลพื้นหลังของโปรเจกต์ ส่งครั้งแรกครั้งเดียว)

ฉันจะสร้าง "starter" สำหรับเว็บแอปบน Cloudflare ที่นำไปต่อยอดได้ทุกโจทย์ ทำทีละ task ตามที่ฉันสั่งเท่านั้น

เป้าหมาย: โครงเว็บแอปที่ deploy ได้ทันที มีระบบเข้าสู่ระบบและจัดการผู้ใช้แบบง่าย
มีเอกสารและการทดสอบพร้อมให้ต่อยอดแบบ spec-driven

ข้อจำกัด:
- Cloudflare Workers + Hono (TypeScript) + D1 (binding ชื่อ DB, ฐานข้อมูลชื่อ app-db) + Static Assets (โฟลเดอร์ public/)
- ต้องอยู่ใน free plan ห้ามใช้บริการที่ต้องผูกบัตร (Access, R2, Email)
- หน้าเว็บเป็น HTML/CSS/JS ธรรมดา ไม่ใช้ framework รองรับมือถือ
- ห้ามเพิ่ม dependency นอกจาก hono โดยไม่ถาม
- SQL ทุกคำสั่งต้องเป็น prepared statement · เปลี่ยน schema ด้วยไฟล์ migration ใหม่เท่านั้น
- คอมเมนต์และข้อความ error เป็นภาษาไทย · API ตอบ JSON รูปแบบ { "error": "..." } พร้อม status ที่ถูกต้อง
- route 1 เรื่อง = 1 ไฟล์ใน src/routes/

กติกาการทำงาน:
- ห้ามรัน wrangler, npm, git เอง ให้เขียนคำสั่งที่ฉันต้องรันไว้ท้ายคำตอบ
- ถ้าข้อมูลไม่พอ ให้ถามก่อน ห้ามเดา
- จบแต่ละ task ตอบ 3 ส่วน: ไฟล์ที่แก้ / คำสั่งที่ต้องรัน / วิธีทดสอบ
