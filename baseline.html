ให้ git บอกว่าต่างกันตรงไหน

🎯 ทำขั้นนี้เพื่ออะไร

git diff คือคำสั่งที่แสดงว่าไฟล์เปลี่ยนไปจาก commit ล่าสุดตรงไหนบ้าง ใช้เทียบ spec ได้ละเอียดทีละบรรทัด บรรทัดสีแดง (-) คือของคุณ บรรทัดสีเขียว (+) คือฉบับอ้างอิง

พิมพ์ใน Git Bash คำสั่งแรกสรุปว่าไฟล์ไหนต่างกันกี่บรรทัด คำสั่งที่สองแสดงความต่างของ SRS ทีละบรรทัด

git diff --stat
git diff docs/SRS.md

ระหว่างอ่าน กด Space เพื่อเลื่อนหน้า และกด q เพื่อออก ถ้าอยากอ่านง่ายกว่านี้ ให้เปิด VS Code ไปที่แท็บ Source Control แล้วคลิกชื่อไฟล์ จะเห็นของเดิมกับของใหม่วางคู่กัน

จดตาราง 4 ช่อง

🎯 ทำขั้นนี้เพื่ออะไร

แยกให้ชัดว่า spec ของเราต่างจากฉบับอ้างอิงแบบไหน เพราะแต่ละแบบบอกเราคนละเรื่อง จดลงกระดาษหรือไฟล์โน้ตของคุณเองก็ได้

ช่องความหมายคำถามนำของฉัน (จดอย่างน้อยช่องละ 1)
✅ ตรงกันrequirement ที่เราเขียนไว้ถูกคำตอบ Q1–Q12 ข้อไหนที่ AI เขียนลง SRS ถูกต้อง?
❌ ตกหล่นฉบับอ้างอิงมี แต่ของเราไม่มีทุกคนได้คำตอบครบ 12 ข้อ แต่ SRS ที่ AI เขียนใส่ครบไหม? ดูกรณี “ต่อคิวพอดี” (Q1) · “คนเกินที่นั่ง” (Q5) · “ห้ามจองย้อนหลัง” (Q2) · “เห็นแค่ช่วงเวลาไม่เห็นชื่อ” (Q6) — ถ้าหล่นไป ระบบจะสร้างผิดอย่างไร?
⚠ แต่งเพิ่มอยู่ในของเรา แต่ไม่มีที่มาในโจทย์หรือคำตอบAI เพิ่มอะไรเอง? (แจ้งเตือน LINE, รายงานสถิติ, OTP…) เราสังเกตเห็นไหมว่าข้อนั้นไม่มีที่มา?
💡 ดีกว่าไอเดียดีที่ฉบับอ้างอิงไม่มีมีอะไรที่เจ้าของโจทย์น่าจะอยากได้? ให้จดไว้ใน backlog เพื่อเสนอในรอบหน้า

แชร์กับเพื่อนข้าง ๆ: 1 ข้อที่ตกหล่นแล้วจะทำให้ระบบผิด และ 1 ข้อที่ AI แต่งเพิ่ม

Non-functional Requirements + วิธีตรวจ (SRS §5)

Non-functional requirement (NFR) คือคุณภาพที่ระบบต้องมี เช่น ใช้บนมือถือได้ เร็วพอ ปลอดภัย ไม่ใช่ฟีเจอร์ที่กดใช้ได้โดยตรง

รหัสเกณฑ์ที่วัดได้วิธีตรวจ
NFR-01ใช้ทุกหน้าได้บนจอ 375px ไม่มี scroll แนวนอนสาธิต (demonstration)
NFR-02ผู้ใช้ที่เคยใช้แล้วจองเสร็จภายใน 1 นาทีสาธิต + จับเวลา
NFR-03รหัสผ่านเก็บเป็น hash + saltตรวจ (inspection)
NFR-04เห็น/ยกเลิกการจองของคนอื่นไม่ได้ทดสอบ (AC-3.1, AC-3.3)
NFR-05ใช้เฉพาะบริการฟรีที่ไม่ผูกบัตรตรวจ (inspection)
NFR-06เวลาไทย YYYY-MM-DDTHH:MM ทั้งระบบทดสอบ (AC-2.5) + ตรวจข้อมูล

ไม่ใช่ทุก requirement จะตรวจด้วยโปรแกรมทดสอบอัตโนมัติได้ แต่ทุกข้อต้องมีวิธีตรวจ ได้แก่ ทดสอบ (test) · สาธิตให้ดู (demonstration) · เปิดดูโดยตรง (inspection) · วิเคราะห์ (analysis)

🎯 ทำขั้นนี้เพื่ออะไร

trace คือสคริปต์ในโปรเจกต์ที่ไล่ดูว่า AC แต่ละข้อใน SPEC มีเคสทดสอบรองรับแล้วหรือยัง ตอนนี้ SPEC มี AC ของระบบจองรถแล้ว แต่ยังไม่มีโค้ดและเคสทดสอบ trace จึงจะแสดง ❌ ขาด ทุก AC ของระบบจองรถ รายการ ❌ เหล่านี้คืองานที่ต้องทำช่วงบ่าย

พิมพ์ใน Git Bash

npm run trace

ถือว่าถูกต้องเมื่อเห็น AC ที่มากับโปรเจกต์ตั้งต้น (starter) เช่น AC-0.1, AC-A… เป็น ✅ และ AC-1.x – AC-4.x เป็น ❌ หลายข้อ และ trace บอกว่า FR ทุกข้อใน SRS ถูกอ้างถึงใน SPEC แล้ว

✅ ผ่านช่วงนี้เมื่อ
  • จดตาราง 4 ช่องครบอย่างน้อยช่องละ 1 ข้อ
  • มี commit “adopt baseline spec”
  • npm run trace แสดง AC ของโจทย์ที่ยังขาดเคสทดสอบ — พร้อมเริ่ม Lab 3
