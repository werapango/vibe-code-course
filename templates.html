## 3. User Stories + Acceptance Criteria

### ✅ ส่วนที่ starter มีให้แล้ว (ตัวอย่าง spec ที่ตรวจสอบได้ — ห้ามลบ)

#### US-0 ตรวจสถานะระบบ
ในฐานะผู้ดูแลระบบ ฉันต้องการเช็กว่าเซิร์ฟเวอร์และฐานข้อมูลพร้อม เพื่อรู้ว่าปัญหาอยู่ที่ระบบหรือที่เครือข่าย
- **AC-0.1** Given เซิร์ฟเวอร์ทำงานและรัน migration แล้ว When `GET /api/health` Then ได้ 200 `{ ok: true, db: "ready" }`

#### US-A1 ตั้งค่าครั้งแรก
ในฐานะผู้ติดตั้งระบบ ฉันต้องการสร้างผู้ดูแลระบบคนแรกจากหน้าเว็บ เพื่อเริ่มใช้งานได้โดยไม่ต้องแก้ฐานข้อมูลเอง
- **AC-A1.1** Given ระบบยังไม่มีผู้ใช้ When `POST /api/auth/setup` ด้วยชื่อและรหัสที่ถูกกติกา Then ได้ 201, ผู้ใช้นั้นเป็น `admin` และล็อกอินอยู่ทันที
- **AC-A1.2** Given ระบบมีผู้ใช้อย่างน้อย 1 คน When `POST /api/auth/setup` Then ได้ 409 (ตั้งค่าซ้ำไม่ได้)

#### US-A2 เข้าสู่ระบบ / ออกจากระบบ
ในฐานะผู้ใช้ ฉันต้องการเข้าสู่ระบบด้วยชื่อและรหัสผ่าน เพื่อใช้งานในนามของตัวเอง
- **AC-A2.1** Given ชื่อและรหัสถูก When `POST /api/auth/login` Then ได้ 200 และ cookie `session` แบบ HttpOnly
- **AC-A2.2** Given รหัสผิด หรือไม่มีชื่อนี้ When ล็อกอิน Then ได้ 401 ด้วย**ข้อความเดียวกัน**ทั้งสองกรณี
- **AC-A2.3** Given ไม่ได้ล็อกอิน When `GET /api/auth/me` Then ได้ 401
- **AC-A2.4** Given ล็อกอินอยู่ When `POST /api/auth/logout` Then session เดิมใช้ไม่ได้อีก (`/api/auth/me` ได้ 401)

#### US-A3 เปลี่ยนรหัสผ่านของตัวเอง
ในฐานะผู้ใช้ ฉันต้องการเปลี่ยนรหัสผ่านเอง เพื่อดูแลความปลอดภัยของบัญชี
- **AC-A3.1** Given ใส่รหัสเดิมถูก และรหัสใหม่ยาว 8–100 ตัว When `PUT /api/auth/password` Then ได้ 200 และล็อกอินด้วยรหัสใหม่ได้
- **AC-A3.2** Given ใส่รหัสเดิมผิด When เปลี่ยนรหัส Then ได้ 400 และรหัสไม่เปลี่ยน

#### US-A4 จัดการผู้ใช้ (admin)
ในฐานะผู้ดูแลระบบ ฉันต้องการเพิ่ม แก้ role ตั้งรหัสใหม่ และลบผู้ใช้ เพื่อควบคุมว่าใครเข้าระบบได้
- **AC-A4.1** Given ผู้ใช้ role `user` When เรียก `/api/users` ใด ๆ Then ได้ 403
- **AC-A4.2** Given admin When `POST /api/users` (ชื่อ, รหัส, role ไม่บังคับ) Then ได้ 201, role เริ่มต้นเป็น `user` และคำตอบไม่มี `password_hash`
- **AC-A4.3** Given มีชื่อผู้ใช้นี้แล้ว When เพิ่มชื่อซ้ำ Then ได้ 409

# AGENTS.md — คู่มือประจำโปรเจกต์สำหรับ AI agent

> ไฟล์นี้ถูกอ่านเป็น context แรกทุกครั้งที่เปิด session ใหม่
> เขียนสิ่งที่ "ต้องบอก agent ทุกครั้ง" ไว้ที่นี่ แทนการพิมพ์ซ้ำในทุก prompt

## โปรเจกต์นี้คืออะไร
- ข้อกำหนดสำหรับลงมือทำ: `SPEC.md` (AC, data model, API contract) — **อ่านก่อนทุก task**
- รายการงาน: `TASKS.md` (WBS)
- เอกสารฉบับเต็มสำหรับคน: `docs/SRS.md`, `docs/DESIGN.md` — อ่านเฉพาะเมื่อ SPEC.md ไม่พอ

## Stack
- Cloudflare Workers + Hono (TypeScript) — API อยู่ใน `src/`
- หน้าเว็บ: HTML + CSS + JavaScript ธรรมดา ไม่ใช้ framework — อยู่ใน `public/`
- ฐานข้อมูล: Cloudflare D1 (SQLite) binding ชื่อ `DB` ฐานข้อมูลชื่อ `app-db` — schema อยู่ใน `migrations/`
- ทดสอบ: `scripts/smoke.mjs` (เรียก API จริง) + `scripts/trace.mjs` (ตรวจว่าทุก AC มีเคสทดสอบ)

## กติกาการทำงาน (สำคัญ)
1. **ทำทีละ 1 task จาก TASKS.md** ตามที่ผู้ใช้สั่งเท่านั้น ห้ามทำ task อื่นล่วงหน้า
2. **ห้ามรันคำสั่งเหล่านี้เอง:** `wrangler` ทุกคำสั่ง, `npm install`, `git` — เขียนคำสั่งที่ผู้ใช้ต้องรันไว้ท้ายคำตอบ ผู้ใช้จะรันเองแล้วแปะผลกลับมาถ้ามีปัญหา
3. อ่านเฉพาะไฟล์ที่เกี่ยวกับ task — ห้ามอ่าน `node_modules/`, `.wrangler/`, `package-lock.json`
4. ถ้า SPEC.md ไม่ได้บอก (เช่น ไม่รู้ว่าควรตอบ status อะไร) **ให้ถามก่อน ห้ามเดา**
5. จบ task ทุกครั้ง ตอบสั้น ๆ 3 ส่วน: **ไฟล์ที่แก้**, **คำสั่งที่ผู้ใช้ต้องรัน**, **วิธีทดสอบ** และเปลี่ยนสถานะ task ใน TASKS.md เป็น `[x]`
6. ห้ามเพิ่ม dependency ใหม่ โดยไม่ถามก่อน

## กติกาของโค้ด
- ตอบและเขียนคอมเมนต์เป็นภาษาไทย
- SQL ทุกคำสั่งต้องเป็น prepared statement (`.prepare(...).bind(...)`) ห้ามต่อ string
- เปลี่ยน schema = สร้างไฟล์ migration ใหม่เท่านั้น **ห้ามแก้ไฟล์ migration ที่มีอยู่แล้ว**
- route ที่ต้องล็อกอินใช้ `requireAuth` จาก `src/lib/auth.ts` · ข้อมูลที่เป็นของผู้ใช้ต้องกรองด้วย `c.get("userId")` เสมอ
- API ตอบ JSON เสมอ — error ใช้รูปแบบ `{ "error": "ข้อความภาษาไทย" }` พร้อม status ที่ถูกต้อง (400, 401, 403, 404, 409)
- เวลาในระบบเก็บเป็นข้อความ `YYYY-MM-DDTHH:MM` (เวลาท้องถิ่น) ยกเว้นที่ระบุไว้ใน SPEC.md
- หน้าเว็บ: แสดงข้อมูลผู้ใช้ผ่าน `esc()` เสมอ (กัน XSS)
- ทุก AC ใหม่ต้องมีเคสใน `scripts/smoke.mjs` ชื่อเคสขึ้นต้นด้วยรหัส AC

## ส่วนที่ 1 — บริบท (ส่งครั้งแรกครั้งเดียว หรือบันทึกเป็นไฟล์ให้ agent อ่าน)

```
ฉันจะสร้าง "starter" สำหรับเว็บแอปบน Cloudflare ที่นำไปต่อยอดได้ทุกโจทย์ ทำทีละ task ตามที่ฉันสั่งเท่านั้น

เป้าหมาย: โครงเว็บแอปที่ deploy ได้ทันที มีระบบเข้าสู่ระบบและจัดการผู้ใช้แบบง่าย
มีเอกสารและการทดสอบพร้อมให้ต่อยอดแบบ spec-driven

ข้อจำกัด:
- Cloudflare Workers + Hono (TypeScript) + D1 (binding ชื่อ DB, ฐานข้อมูลชื่อ app-db) + Static Assets (โฟลเดอร์ public/)
- ต้องอยู่ใน free plan ห้ามใช้บริการที่ต้องผูกบัตร (Access, R2, Email)
- หน้าเว็บเป็น HTML/CSS/JS ธรรมดา ไม่ใช้ framework รองรับมือถือ
- ห้ามเพิ่ม dependency นอกจาก hono โดยไม่ถาม
- SQL ทุกคำสั่งต้องเป็น prepared statement · เปลี่ยน schema ด้วยไฟล์ migration ใหม่เท่านั้น
- คอมเมนต์และข้อความ error เป็นภาษาไทย · API ตอบ JSON รูปแบบ { "error": "..." } พร้อม status ที่ถูกต้อง
- route 1 เรื่อง = 1 ไฟล์ใน src/routes/

กติกาการทำงาน:
- ห้ามรัน wrangler, npm, git เอง ให้เขียนคำสั่งที่ฉันต้องรันไว้ท้ายคำตอบ
- ถ้าข้อมูลไม่พอ ให้ถามก่อน ห้ามเดา
- จบแต่ละ task ตอบ 3 ส่วน: ไฟล์ที่แก้ / คำสั่งที่ต้องรัน / วิธีทดสอบ
```

## ส่วนที่ 2 — 👤 คนรันเองก่อนเริ่ม

```bash
npm create cloudflare@latest my-app -- --category=hello-world --type=hello-world-with-assets --lang=ts --no-deploy --no-git --no-agents
cd my-app
npm install hono
git init
```

## ส่วนที่ 3 — task (ส่งให้ agent ทีละข้อ แล้ว commit หลังแต่ละข้อ)

**T1 โครงแอป**
```
ทำ T1: แปลง src/index.ts เป็น Hono แยก route ไว้ใน src/routes/ เพิ่ม GET /api/health ตอบ { ok: true, db, time }
โดย db บอกสถานะฐานข้อมูล ("ready" / "no-binding" / "not-migrated"), ดัก 404 และ 500 เป็น JSON,
ตั้ง wrangler.jsonc ให้มี assets (public/) และ observability พร้อมคอมเมนต์ภาษาไทยทุกส่วน
เสร็จเมื่อ: npm run dev แล้ว /api/health ตอบ 200 และหน้า public/index.html เรียก API นี้แสดงผลได้
```

**T2 การทดสอบ**
```
ทำ T2: สร้าง scripts/smoke.mjs (เรียก API จริง, จำ cookie ได้แบบเบราว์เซอร์, เปลี่ยน local/production ด้วย BASE_URL,
ชื่อเคสขึ้นต้นด้วยรหัส AC, รายงาน ผ่าน/ไม่ผ่าน/ข้าม) และ scripts/trace.mjs (ตรวจว่า AC ตัวหนาทุกข้อใน SPEC.md
มีเคสใน smoke.mjs และทุกเคสอ้าง AC ที่มีจริง, เตือนถ้า FR ใน docs/SRS.md ไม่ถูกอ้างใน SPEC.md)
เพิ่ม npm scripts: dev, deploy, smoke, trace
```

👤 หลัง T2 สร้างฐานข้อมูล:
```bash
npx wrangler d1 create app-db --binding DB --update-config
```

**T3 ฐานข้อมูลผู้ใช้ + ไลบรารี auth**
```
ทำ T3: migration ตาราง users (username unique, password_hash, role admin/user, created_at)
และ sessions (token, user_id อ้าง users ลบตาม, expires_at) + src/lib/auth.ts:
hash ด้วย PBKDF2-SHA256 100,000 รอบ + salt สุ่ม เก็บเป็น "salt:hash", session token สุ่ม 32 ไบต์ อายุ 7 วัน,
cookie HttpOnly + SameSite=Lax (Secure เมื่อเป็น https), middleware requireAuth (ฝาก userId, username, role ใน context)
และ requireAdmin (403 ถ้าไม่ใช่ admin)
```

👤 หลัง T3:
```bash
npx wrangler d1 migrations apply app-db --local
```

**T4 API ผู้ใช้**
```
ทำ T4: /api/auth/setup (GET บอกว่ายังไม่มีผู้ใช้ไหม, POST สร้าง admin คนแรกได้เฉพาะตอนยังไม่มีผู้ใช้ แล้วล็อกอินให้),
login, logout, me, PUT password (เปลี่ยนรหัสของตัวเอง ต้องยืนยันรหัสเดิม)
และ /api/users CRUD สำหรับ admin เท่านั้น (ไม่ส่ง password_hash ออกไป)
กติกา: ล็อกอินผิดตอบข้อความเดียวกันไม่ว่าชื่อหรือรหัสผิด, admin ลบตัวเองไม่ได้, ต้องเหลือ admin อย่างน้อย 1 คน,
admin ตั้งรหัสใหม่ให้ใครแล้ว session เดิมของคนนั้นต้องใช้ไม่ได้
เพิ่มเคส smoke ครบทุกกติกา
```

**T5 หน้าเว็บ**
```
ทำ T5: หน้าเดียวหลาย view สลับด้วย #hash: ตั้งค่าครั้งแรก, ล็อกอิน, หน้าหลัก (แสดง /api/health),
จัดการผู้ใช้ (admin), เปลี่ยนรหัสผ่าน · แยกไฟล์ index.html / app.css / app.js
ทุกหน้าใช้ fetch เรียก API แสดง error จาก API และ escape ข้อมูลผู้ใช้ก่อนแสดง (กัน XSS)
```

**T6 เอกสาร**
```
ทำ T6: AGENTS.md (stack, โครงไฟล์, กติกาการทำงานแบบในส่วนที่ 1, ตาราง skills),
SPEC.md (ส่วนผู้ใช้และการเข้าสู่ระบบเขียนครบเป็นตัวอย่าง: user story, AC แบบ Given/When/Then ตัวหนาพร้อมรหัส,
data model, API contract, NFR ที่วัดได้) + template เปล่าของ TASKS.md, docs/SRS.md, docs/DESIGN.md,
skills/add-endpoint/SKILL.md, README.md
```

## ส่วนที่ 4 — 👤 ตรวจทุก task

```bash
npm run dev
npm run smoke
npm run trace
git add . && git commit -m "Tn: ..."
```

ทำไมไฟล์เหล่านี้ประหยัด token

  • เขียนครั้งเดียว ใช้ทุก task — แทนการพิมพ์ spec และกติกาซ้ำในทุก prompt
  • AC ชัด + ตารางตัวอย่าง — agent ไม่ต้องเดา จึงไม่ต้องวนแก้หลายรอบ
  • แยกฉบับคน (SRS/DESIGN) กับฉบับ agent (SPEC) — agent อ่านเฉพาะส่วนที่จำเป็น context จึงเล็ก
  • skill โหลดเมื่อจำเป็น — ไม่กิน context ในงานที่ไม่เกี่ยว
  • trace ตรวจแทนการถาม agent — "ครบทุก AC หรือยัง" ตอบได้ด้วยสคริปต์ ไม่ใช้ token
