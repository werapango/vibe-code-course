บอกบทบาทให้ AI และให้มันตั้งคำถามก่อน · 4 นาที

🎯 ทำขั้นนี้เพื่ออะไร

เริ่มด้วยการถาม ไม่ใช่การเขียน — ให้ AI ช่วยหาจุดกำกวมในโจทย์ แทนที่จะปล่อยให้มันเดาคำตอบเอง

💬 วาง prompt นี้ แล้วแปะข้อความโจทย์ทั้งหมดต่อท้าย
คุณคือนักวิเคราะห์ความต้องการ (business analyst) ที่ช่วยฉันเขียน SRS
ด้านล่างคือบันทึกจากเจ้าของโจทย์ แต่ละย่อหน้ามีเลข B1–B7 กำกับ

งานแรก: ยังไม่ต้องเขียนอะไร ให้ตั้งคำถามที่ต้องถามเจ้าของโจทย์ก่อนเขียน requirement ได้ ไม่เกิน 10 ข้อ
- เน้นคำที่ตีความได้หลายแบบ สิ่งที่ขาดหาย และกติกาที่ยังไม่ชัด
- แต่ละข้อบอกว่ามาจาก B ไหน และถ้าไม่ถามจะสร้างผิดได้อย่างไร
- ห้ามเดาคำตอบ

บันทึกจากเจ้าของโจทย์:
[แปะข้อความโจทย์ทั้งหมด]

ตรวจคำตอบ: คำถามชี้ไปที่คำกำกวมจริงไหม (เช่น “ห้ามจองชน”, “ล่วงหน้า”, “นั่งไม่พอ”, “ยกเลิกได้”) หรือเป็นคำถามทั่วไปที่ใช้กับระบบไหนก็ได้?

👤 ถามเจ้าของโจทย์ (ผู้สอน) · 6 นาที

🎯 ทำขั้นนี้เพื่ออะไร

ขั้นนี้เรียกว่า validation (การยืนยันความต้องการ) คือถามคนที่รู้ความต้องการจริง เพราะ AI ตอบแทนเจ้าของโจทย์ไม่ได้

  1. เลือกคำถามที่สำคัญที่สุด 3–5 ข้อ (ข้อที่ถ้าตอบผิดจะทำให้ระบบผิด)
  2. ยกมือถามผู้สอนซึ่งรับบท “หัวหน้างานยานพาหนะ” หรือฟังคำตอบที่เพื่อนถามแล้ว
  3. จดคำถามและคำตอบลงใน docs/SRS.md หัวข้อที่ 8 (§8) โดยตั้งรหัสเป็น Q1, Q2, … ตามลำดับ
  4. คำถามที่ไม่ได้ถาม ให้จดใน §8 เหมือนกัน พร้อมเขียนว่าคุณสมมติคำตอบไว้อย่างไร และติดป้าย [สมมติฐาน]
💬 แปะคำตอบที่ได้กลับไปในแชต AI
นี่คือคำตอบจากเจ้าของโจทย์ ใช้รหัส Q เป็นที่มาได้ ข้อที่ไม่มีคำตอบให้ถือเป็นสมมติฐาน:
Q1: [คำถาม] → [คำตอบ]
Q2: [คำถาม] → [คำตอบ]
...

Stakeholder + Use case · 5 นาที

🎯 ทำขั้นนี้เพื่ออะไร

หาว่าใครเกี่ยวข้องกับระบบบ้าง เรียกว่า stakeholder (รวมคนที่ไม่ได้ใช้ระบบแต่ได้รับผล) และระบบต้องรองรับ “งาน” อะไรบ้าง — use case คืองานแต่ละอย่างที่ผู้ใช้ทำกับระบบ (เช่น “จองรถ”) การเขียน use case ช่วยให้คิดครบทั้งขั้นตอนปกติและกรณีผิดปกติ

จากโจทย์และคำตอบ เขียนเป็น Markdown:
1) ตาราง stakeholders: กลุ่ม | บทบาท/สิ่งที่ต้องการ | ใช้ระบบไหม
2) ตารางรายการ use case: รหัส UC-01.. | ชื่อ | actor
3) use case "จองรถ" แบบละเอียด: actor, precondition, main flow เป็นข้อ ๆ,
   alternate flows (เช่น เวลาซ้อน คนเกินที่นั่ง เวลาไม่ถูกต้อง), postcondition
ระบบมีระบบผู้ใช้/ล็อกอิน/admin จัดการบัญชีอยู่แล้ว ไม่ต้องออกแบบส่วนนั้นใหม่

วางลง: docs/SRS.md §2 และ §3 · ตรวจ: กรณีผิดปกติ (alternate flow) ครอบคลุมกติกาในโจทย์ครบไหม และมีผู้ใช้ (actor) ที่โจทย์ไม่ได้พูดถึงโผล่มาไหม — ถ้ามี แปลว่า AI แต่งเพิ่มเอง

4

Functional Requirements พร้อมที่มา · 6 นาที

🎯 ทำขั้นนี้เพื่ออะไร

Functional Requirement (FR) คือสิ่งที่ระบบต้องทำได้ · ขั้นนี้เปลี่ยนความต้องการเป็นข้อ ๆ ที่ตรวจได้ (ทดสอบได้ว่าทำแล้วหรือยัง) และตามรอยได้ (ชี้ได้ว่ามาจากย่อหน้าไหนของโจทย์ หรือคำตอบข้อไหน) — ทุกข้อมีรหัส ที่มา และลำดับความสำคัญ

เขียนตาราง Functional Requirements:
รหัส FR-01.. | ระบบต้อง... | ที่มา (B# หรือ Q#) | ความสำคัญ (ต้องมี / ควรมี / อาจทำ / ยังไม่ทำ) | use case
กติกา:
- 1 ข้อ = 1 ความสามารถ ขึ้นต้นด้วย "ระบบต้อง" และตรวจได้ว่าทำแล้วหรือยัง
- ข้อที่ไม่มีที่มาในโจทย์หรือคำตอบ ให้ใส่ที่มาว่า [สมมติฐาน] ห้ามแต่งที่มา
- สิ่งที่เจ้าของโจทย์บอกว่า "ไว้รอบหน้า" ให้ใส่ความสำคัญเป็น ควรมี หรือ ยังไม่ทำ

วางลง: docs/SRS.md §4 · ตรวจ: ไล่ดูทุกแถวที่มี [สมมติฐาน] แล้วเลือกว่าจะตัดทิ้ง หรือย้ายไปเป็นคำถามใน §8 · ดูว่ามีกติกา “ห้ามจองชน” “นั่งไม่พอ” “แก้ของคนอื่นไม่ได้” ครบไหม

Non-functional Requirements ที่วัดได้ · 4 นาที

🎯 ทำขั้นนี้เพื่ออะไร

Non-functional Requirement (NFR) คือคุณภาพของระบบ เช่น ความเร็ว ความปลอดภัย ความง่ายในการใช้ (ไม่ใช่ฟังก์ชัน) · NFR ที่ดีต้องวัดได้และบอกวิธีตรวจ ตัวอย่าง: “ใช้ง่าย” ตรวจไม่ได้ แต่ “จองเสร็จใน 1 นาทีบนจอกว้าง 375px” ตรวจได้

เขียนตาราง Non-functional Requirements:
รหัส NFR-01.. | ด้าน (ความปลอดภัย/ใช้งาน/ประสิทธิภาพ/ค่าใช้จ่าย/ความถูกต้อง) | เกณฑ์ที่วัดได้เป็นตัวเลขหรือผ่าน/ไม่ผ่าน | วิธีตรวจ | ที่มา
วิธีตรวจเลือกจาก: ทดสอบ (test) / สาธิต (demonstration) / ตรวจ (inspection) / วิเคราะห์ (analysis)
ห้ามใช้คำกว้าง ๆ เช่น "ใช้ง่าย" "เร็ว" "ปลอดภัย" โดยไม่มีเกณฑ์

วางลง: docs/SRS.md §5 (และข้อจำกัด เช่น “ฟรี ไม่ผูกบัตร” ลง §6)

User story + Acceptance criteria + ตารางตัวอย่าง · 6 นาที

🎯 ทำขั้นนี้เพื่ออะไร

user story คือความต้องการที่เขียนจากมุมของผู้ใช้ ส่วน acceptance criteria (AC) คือเงื่อนไขที่ตกลงกันว่าแบบไหนถือว่า “ทำถูก” เขียนแบบ Given/When/Then (กำหนดให้… / เมื่อ… / แล้วต้อง…) · ตารางตัวอย่างพร้อมผลที่คาดหวังที่เขียนก่อนเขียนโค้ด จะถูกนำไปใช้เป็นเคสทดสอบตอนบ่าย

สำหรับ FR ระดับ "ต้องมี" เขียน user story รูปแบบ "ในฐานะ ... ฉันต้องการ ... เพื่อ ..."
แต่ละ story มี acceptance criteria แบบ Given / When / Then รหัส AC-1.1, AC-1.2, ...
ระบุผลที่ตรวจได้ เช่น HTTP status (201, 400, 401, 403, 404, 409) หรือข้อมูลที่ต้องเห็น
แล้วทำ "ตารางตัวอย่าง" ของกติกาเวลาจองซ้อน:
สมมติรถ A ถูกจอง 10:00–12:00 ไว้แล้ว ให้ 8 กรณีการจองใหม่ (ทับบางส่วน, อยู่ข้างใน, คลุมทั้งช่วง, ต่อคิวพอดี, คนละคัน ฯลฯ)
คอลัมน์: # | การจองใหม่ | ผลที่คาดหวัง | เหตุผล
ถ้ากรณีไหนโจทย์ยังไม่ได้ตัดสิน ให้เขียนว่า "ต้องถามเจ้าของโจทย์"

วางลง: ท้าย docs/SRS.md หรือใน SPEC.md §3 ส่วนของโจทย์ · ตรวจ: กรณี “ต่อคิวพอดี” (เช่น การจองใหม่เริ่ม 12:00 ตรงกับเวลาที่การจองเดิมจบ) AI ตอบตามคำตอบของเจ้าของโจทย์ หรือเดาเอง?

ร่าง Design · 6 นาที

🎯 ทำขั้นนี้เพื่ออะไร

เปลี่ยนจาก “ระบบต้องทำอะไร” เป็น “จะสร้างอย่างไร”: โครงสร้างระบบ (สถาปัตยกรรม), การตัดสินใจสำคัญพร้อมเหตุผล (ADR — Architecture Decision Record), ตารางข้อมูลที่ต้องเก็บ และ API · prompt นี้บอกข้อจำกัดจริงที่คุณเจอใน Lab 1 (Cloudflare แบบฟรี และ starter ที่มีระบบล็อกอินแล้ว) เพื่อไม่ให้ AI เสนอสิ่งที่ใช้ไม่ได้

จาก SRS ข้างต้น ร่าง design เป็น Markdown โดยมีข้อจำกัดดังนี้:
- deploy บน Cloudflare Workers + Hono (TypeScript) + D1 (SQLite) free plan ห้ามใช้บริการที่ต้องผูกบัตร
- มี starter แล้ว: ตาราง users (role admin/user), sessions, API ล็อกอิน, middleware requireAuth / requireAdmin
หัวข้อ:
1) แผนภาพสถาปัตยกรรมแบบข้อความ (เบราว์เซอร์ → Worker → D1)
2) ADR อย่างน้อย 1 ข้อ เรื่องที่ deploy/tech stack: บริบท, ตัวเลือก 3 แบบ, ตัดสินใจ, เหตุผล, ผลที่ตามมา
   และ ADR เรื่องจะตรวจกติกาเวลาซ้อนที่ไหนและอย่างไร
3) entity + ความสัมพันธ์ และตารางใหม่ (คอลัมน์, ชนิด, constraint, มาจาก FR ไหน)
4) รายการ API: method | path | use case | สิทธิ์ (ใครเรียกได้)
5) ตาราง NFR → การออกแบบ

วางลง: docs/DESIGN.md §2–§6 · ตรวจ: AI เสนอบริการที่ต้องผูกบัตร หรือสร้างระบบล็อกอินใหม่ซ้ำกับ starter ไหม?

8

ให้ AI รีวิว แต่คนตัดสิน · 3 นาที

🎯 ทำขั้นนี้เพื่ออะไร

ให้ AI ช่วยตรวจอีกรอบเพื่อหาจุดอ่อน — แต่คุณเป็นคนเลือกว่าจะแก้ข้อไหน

รีวิว SRS ทั้งหมดที่เราเขียนในแชตนี้ ตอบเป็นรายการสั้น ๆ ไม่เกิน 8 ข้อ:
- requirement ที่กำกวมหรือตรวจไม่ได้
- requirement ที่ขัดกันเอง
- requirement ที่ไม่มีที่มาจากโจทย์หรือคำตอบ (อาจถูกแต่งขึ้น)
- กรณีผิดปกติที่ยังไม่มี AC รองรับ
ห้ามเขียน SRS ใหม่ทั้งหมด

อ่านรายการที่ AI ส่งมา แล้วแก้ในไฟล์ของคุณเฉพาะข้อที่คุณเห็นด้วย

เช็กคุณภาพ requirement (ทำเอง 2 นาที)

คุณสมบัติถามตัวเองตัวอย่างที่ไม่ผ่าน → ผ่าน
ไม่กำกวมคนสองคนอ่านแล้วเข้าใจตรงกันไหม“ห้ามจองชน” → “ห้ามจองรถคันเดียวกันที่ช่วงเวลาทับกัน” + ระบุให้ชัดว่าต่อคิวพอดีนับว่าทับไหม (ยังไม่รู้ → ถามเจ้าของโจทย์)
ตรวจสอบได้มีวิธีพิสูจน์ว่าผ่าน/ไม่ผ่านไหม“ใช้บนมือถือได้” → “ทุกหน้าใช้ได้บนจอ 375px ไม่มี scroll แนวนอน”
มีที่มาบอกได้ไหมว่ามาจาก B# หรือ Q# ไหน“ส่ง LINE แจ้งเตือน” (ไม่มีในโจทย์) → ติด [สมมติฐาน] หรือตัดออก
ไม่ขัดกันมีสองข้อที่ทำพร้อมกันไม่ได้ไหม“ยกเลิกได้ทุกเมื่อ” กับ “ยกเลิกได้ก่อนเวลาเริ่ม”
ครบกรณีผิดปกติมี AC รองรับไหมมีแต่ “จองได้” ไม่มี “จองไม่ได้เพราะ…”
จัดลำดับแล้วรู้ไหมว่าข้อไหนต้องมีในรอบแรกทุกข้อเป็น “ต้องมี” → แยก ต้องมี / ควรมี / ยังไม่ทำ

AI เสนอ Firebase / AWS / ส่งอีเมล / OTPย้ำข้อจำกัด: Cloudflare free plan ไม่ผูกบัตร และมีระบบล็อกอินจาก starter แล้ว
