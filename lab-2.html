รอบ 1 · ให้ AI ช่วยหาคำถามก่อนเขียน (4 นาที)

🎯 ทำขั้นนี้เพื่ออะไร

รอบ 2 · 👤 ถามเจ้าของโจทย์ แล้วบอก AI (6 นาที)

🎯 ทำขั้นนี้เพื่ออะไร

ขั้นนี้เรียกว่า validation (การยืนยันความต้องการกับคนที่รู้จริง) AI ตอบแทนเจ้าของโจทย์ไม่ได้ เพราะมันไม่รู้ว่าหน่วยงานนี้ต้องการอะไร

  1. ผู้สอนรับบท “หัวหน้างานยานพาหนะ” ยกมือถามคำถามของคุณ หรือฟังคำตอบที่เพื่อนถาม (คำตอบใช้ได้กับทุกคน)
  2. จดคำตอบลงช่อง “คำตอบ” ในหัวข้อ 8 ของ docs/SRS.md ให้ตรงกับคำถามแต่ละข้อ
  3. คำถามที่ไม่ได้ถาม ให้เขียนว่าคุณสมมติคำตอบไว้อย่างไร แล้วติดป้าย [สมมติฐาน]
| Q1 | (B6) "จองล่วงหน้า" ได้ไกลสุดกี่วัน? | เจ้าของโจทย์ | [คำตอบที่ได้จากผู้สอน] |
| Q2 | (B2) ต้องกรอกจำนวนผู้โดยสารไหม? | เจ้าของโจทย์ | [สมมติฐาน] สมมติว่าต้องกรอก — ยังไม่ได้ถาม |
  1. คัดลอก prompt ด้านล่างไปวางในแชตเดิม แก้บรรทัด Q1, Q2 ให้เป็นคำถามและคำตอบของคุณ (คัดลอกจากตารางที่เพิ่งเขียนได้เลย) แล้วส่ง
นี่คือคำตอบจากเจ้าของโจทย์ ใช้รหัส Q เป็นที่มาได้ ข้อที่ไม่มีคำตอบให้ถือเป็นสมมติฐาน:
Q1: [คำถาม] → [คำตอบ]
Q2: [คำถาม] → [คำตอบ]
...

ทุกแถวในหัวข้อ 8 มีคำตอบ หรือมีป้าย [สมมติฐาน] · AI ตอบรับว่ารับทราบคำตอบแล้ว (ถ้ามันเริ่มเขียน SRS ทั้งเล่มเอง ให้พิมพ์ว่า “หยุดก่อน รอคำสั่งถัดไป”)

รอบ 3 · ผู้เกี่ยวข้อง (stakeholder) + use case (5 นาที)

🎯 ทำขั้นนี้เพื่ออะไร

หาว่าใครเกี่ยวข้องกับระบบบ้าง เรียกว่า stakeholder (รวมคนที่ไม่ได้ใช้ระบบแต่ได้รับผล) และระบบต้องรองรับงานอะไรบ้าง — use case คืองานแต่ละอย่างที่ผู้ใช้ทำกับระบบ เช่น “จองรถ” การเขียนแบบละเอียดช่วยให้คิดครบทั้งขั้นตอนปกติและกรณีผิดปกติ

  1. คัดลอก prompt นี้ไปส่งในแชตเดิม
จากโจทย์และคำตอบ เขียนเป็น Markdown ใน code block:
1) ตาราง stakeholders: กลุ่ม | บทบาท/สิ่งที่ต้องการ | ใช้ระบบไหม
2) ตารางรายการ use case: รหัส UC-01.. | ชื่อ | actor
3) use case "จองรถ" แบบละเอียด: actor, precondition, main flow เป็นข้อ ๆ,
   alternate flows (เช่น เวลาซ้อน คนเกินที่นั่ง เวลาไม่ถูกต้อง), postcondition
ระบบมีระบบผู้ใช้/ล็อกอิน/admin จัดการบัญชีอยู่แล้ว ไม่ต้องออกแบบส่วนนั้นใหม่

👀 AI จะตอบเป็น 3 ส่วน แต่ละส่วนอยู่ในกล่องโค้ดที่มีปุ่ม Copy ของแชตเอง

  1. ส่วนที่ 1 (stakeholders) → กด Copy แล้วไปที่ ## 2. ผู้มีส่วนได้ส่วนเสีย ใน SRS.md ลากคลุมตารางแม่แบบ (แถว | [ ] | [ ] | …) แล้ววางทับ
  2. ส่วนที่ 2 (รายการ use case) → วางทับตารางใน ### 3.1 รายการ use case
  3. ส่วนที่ 3 (จองรถแบบละเอียด) → วางทับแม่แบบใน ### 3.2 รายละเอียด use case หลัก แล้วบันทึก
🔍 ตรวจก่อนไปต่อ

มีกลุ่มคนหรือ actor ที่โจทย์ไม่ได้พูดถึงโผล่มาไหม เช่น “พนักงานขับรถ” หรือ “ฝ่ายการเงิน” — ถ้ามี แปลว่า AI แต่งเพิ่ม ให้ลบออก หรือติดป้าย [สมมติฐาน] · กรณีผิดปกติ (alternate flows) ของ “จองรถ” ครอบคลุมกติกาในโจทย์ไหม (จองชน · นั่งไม่พอ)

✅ ผ่านรอบนี้เมื่อ

หัวข้อ 2 มีอย่างน้อย 2 กลุ่ม · หัวข้อ 3.1 มี use case อย่างน้อย 3 ตัว · หัวข้อ 3.2 มี “จองรถ” พร้อมกรณีผิดปกติอย่างน้อย 2 ข้อ

รอบ 4 · Functional Requirements พร้อมที่มา (6 นาที)

🎯 ทำขั้นนี้เพื่ออะไร

Functional Requirement (FR) คือสิ่งที่ระบบต้องทำได้ รอบนี้สำคัญที่สุดของ lab เพราะตอนบ่ายจะเอาไปเทียบกับฉบับอ้างอิง ทุกข้อต้องตรวจได้ (พิสูจน์ได้ว่าทำแล้วหรือยัง) และตามรอยได้ (ชี้ได้ว่ามาจากย่อหน้าไหนของโจทย์ หรือคำตอบข้อไหน)

  1. คัดลอก prompt นี้ไปส่งในแชตเดิม
เขียนตาราง Functional Requirements เป็น Markdown ใน code block:
รหัส FR-01.. | ระบบต้อง... | ที่มา (B# หรือ Q#) | ความสำคัญ (ต้องมี / ควรมี / อาจทำ / ยังไม่ทำ) | use case
กติกา:
- 1 ข้อ = 1 ความสามารถ ขึ้นต้นด้วย "ระบบต้อง" และตรวจได้ว่าทำแล้วหรือยัง
- ข้อที่ไม่มีที่มาในโจทย์หรือคำตอบ ให้ใส่ที่มาว่า [สมมติฐาน] ห้ามแต่งที่มา
- สิ่งที่เจ้าของโจทย์บอกว่า "ไว้รอบหน้า" ให้ใส่ความสำคัญเป็น ควรมี หรือ ยังไม่ทำ
  1. กด Copy ที่กล่องตารางของ AI แล้ววางทับตารางแม่แบบใน ## 4. Functional Requirements
  2. ตรวจที่มาทีละแถว (ส่วนนี้ AI ทำแทนไม่ได้): ดูเลข B ในช่อง “ที่มา” แล้วเปิดแท็บโจทย์หาย่อหน้านั้น ถามตัวเองว่า “ย่อหน้านี้พูดถึงเรื่องนี้จริงไหม”
  3. แถวที่ที่มาเป็น [สมมติฐาน] หรือที่มาไม่ตรง ให้เลือกอย่างใดอย่างหนึ่ง: ลบทิ้ง หรือย้ายไปเป็นคำถามในหัวข้อ 8 แล้วบันทึกไฟล์
✅ ดี:   | FR-01 | ระบบต้องให้พนักงานที่ล็อกอินแล้วจองรถ โดยเลือกคัน วัน และเวลาเริ่ม–จบ | B3 | ต้องมี | UC-01 |
❌ ระวัง: | FR-09 | ระบบต้องส่งแจ้งเตือนทาง LINE ก่อนถึงเวลาใช้รถ | B1 | ควรมี | - |
         ↑ B1 พูดถึงกลุ่ม LINE ที่ใช้อยู่เดิม ไม่ได้ขอให้แจ้งเตือน → ที่มานี้แต่งขึ้น ให้ลบ หรือเปลี่ยนเป็น [สมมติฐาน]
✅ ผ่านรอบนี้เมื่อ

หัวข้อ 4 มี FR อย่างน้อย 8 ข้อ ทุกข้อขึ้นต้นด้วย “ระบบต้อง” และมีที่มา (B#, Q# หรือ [สมมติฐาน]) · มีกติกา “ห้ามจองชน” “นั่งไม่พอ” และ “แก้การจองของคนอื่นไม่ได้” ครบ

รอบ 5 · Non-functional Requirements ที่วัดได้ (4 นาที)

🎯 ทำขั้นนี้เพื่ออะไร

Non-functional Requirement (NFR) คือคุณภาพของระบบ เช่น ความเร็ว ความปลอดภัย ความง่ายในการใช้ NFR ที่ดีต้องวัดได้และบอกวิธีตรวจ เช่น “ใช้ง่าย” ตรวจไม่ได้ แต่ “จองเสร็จใน 1 นาทีบนจอกว้าง 375px” ตรวจได้

  1. คัดลอก prompt นี้ไปส่งในแชตเดิม
เขียนตาราง Non-functional Requirements เป็น Markdown ใน code block:
รหัส NFR-01.. | ด้าน (ความปลอดภัย/ใช้งาน/ประสิทธิภาพ/ค่าใช้จ่าย/ความถูกต้อง) | เกณฑ์ที่วัดได้เป็นตัวเลขหรือผ่าน/ไม่ผ่าน | วิธีตรวจ | ที่มา
วิธีตรวจเลือกจาก: ทดสอบ (test) / สาธิต (demonstration) / ตรวจ (inspection) / วิเคราะห์ (analysis)
ห้ามใช้คำกว้าง ๆ เช่น "ใช้ง่าย" "เร็ว" "ปลอดภัย" โดยไม่มีเกณฑ์
แล้วแยกรายการข้อจำกัด (constraints) ของโปรเจกต์มาอีกรายการหนึ่ง
  1. ตาราง NFR → วางทับตารางแม่แบบใน ## 5. Non-functional Requirements
  2. รายการข้อจำกัด (เช่น “ใช้ของฟรี ไม่ผูกบัตร” จาก B7) → วางใน ## 6. ข้อจำกัด แล้วบันทึก
✅ ดี:   | NFR-01 | ใช้งาน | ทุกหน้าใช้ได้บนจอกว้าง 375px โดยไม่ต้องเลื่อนซ้าย–ขวา | สาธิต | B3 (จองทางมือถือ) |
❌ ระวัง: | NFR-05 | ประสิทธิภาพ | ระบบต้องเร็ว | ทดสอบ | - |   ← "เร็ว" ไม่มีตัวเลข ตรวจไม่ได้
✅ ผ่านรอบนี้เมื่อ

หัวข้อ 5 มี NFR อย่างน้อย 3 ข้อ ทุกข้อมีเกณฑ์เป็นตัวเลขหรือผ่าน/ไม่ผ่าน และมีวิธีตรวจ · หัวข้อ 6 มีข้อจำกัดเรื่องค่าใช้จ่าย

รอบ 6 · User story + Acceptance criteria + ตารางตัวอย่าง (6 นาที)

🎯 ทำขั้นนี้เพื่ออะไร

user story คือความต้องการที่เขียนจากมุมของผู้ใช้ ส่วน acceptance criteria (AC) คือเงื่อนไขที่ตกลงกันว่าแบบไหนถือว่าทำถูก เขียนแบบ Given / When / Then (กำหนดให้… / เมื่อ… / แล้วต้อง…) · ตารางตัวอย่างที่เขียนก่อนเขียนโค้ด จะกลายเป็นเคสทดสอบตอนบ่าย

  1. คัดลอก prompt นี้ไปส่งในแชตเดิม
สำหรับ FR ระดับ "ต้องมี" เขียน user story รูปแบบ "ในฐานะ ... ฉันต้องการ ... เพื่อ ..."
แต่ละ story มี acceptance criteria แบบ Given / When / Then รหัส AC-1.1, AC-1.2, ...
ระบุผลที่ตรวจได้ เช่น HTTP status (201, 400, 401, 403, 404, 409) หรือข้อมูลที่ต้องเห็น
แล้วทำ "ตารางตัวอย่าง" ของกติกาเวลาจองซ้อน:
สมมติรถ A ถูกจอง 10:00–12:00 ไว้แล้ว ให้ 8 กรณีการจองใหม่ (ทับบางส่วน, อยู่ข้างใน, คลุมทั้งช่วง, ต่อคิวพอดี, คนละคัน ฯลฯ)
คอลัมน์: # | การจองใหม่ | ผลที่คาดหวัง | เหตุผล
ถ้ากรณีไหนโจทย์ยังไม่ได้ตัดสิน ให้เขียนว่า "ต้องถามเจ้าของโจทย์"
ส่งทั้งหมดเป็น Markdown ใน code block
  1. ใน VS Code เปิดไฟล์ SPEC.md (อยู่นอกโฟลเดอร์ docs) เลื่อนไปที่หัวข้อ ### ✍️ ส่วนของโจทย์ (เติมเอง)
  2. วางคำตอบของ AI ทั้งหมดใต้หัวข้อนั้น (ห้ามลบส่วน “✅ ส่วนที่ starter มีให้แล้ว” ที่อยู่ด้านบน) แล้วบันทึก
US-1 ในฐานะพนักงาน ฉันต้องการจองรถเอง เพื่อไม่ต้องโทรถามว่าคันไหนว่าง
- AC-1.1 Given รถ A ว่างช่วง 13:00–15:00  When จองรถ A ช่วงนั้น  Then ได้ 201 และเห็นการจองในรายการของฉัน
- AC-1.2 Given ...
🔍 ตรวจก่อนไปต่อ

ดูแถว “ต่อคิวพอดี” ในตารางตัวอย่าง (การจองใหม่เริ่ม 12:00 ตรงกับเวลาที่การจองเดิมจบ) — AI ตอบตามคำตอบของเจ้าของโจทย์ในรอบ 2 หรือเดาเอง? ถ้าไม่ได้ถามเรื่องนี้ แถวนั้นควรเขียนว่า “ต้องถามเจ้าของโจทย์”

✅ ผ่านรอบนี้เมื่อ

SPEC.md มี user story อย่างน้อย 2 เรื่อง แต่ละเรื่องมี AC แบบ Given/When/Then ที่บอกผลตรวจได้ และมีตารางตัวอย่างเวลาจองซ้อน 8 แถว

รอบ 7 · ร่าง Design (6 นาที)

🎯 ทำขั้นนี้เพื่ออะไร

เปลี่ยนจาก “ระบบต้องทำอะไร” เป็น “จะสร้างอย่างไร”: โครงสร้างระบบ, การตัดสินใจสำคัญพร้อมเหตุผล (ADR — Architecture Decision Record), ตารางข้อมูลที่ต้องเก็บ และ API prompt นี้บอกข้อจำกัดจริงจาก Lab 1 (Cloudflare แบบฟรี และ starter ที่มีระบบล็อกอินแล้ว) เพื่อไม่ให้ AI เสนอสิ่งที่ใช้ไม่ได้

  1. คัดลอก prompt นี้ไปส่งในแชตเดิม
จาก SRS ข้างต้น ร่าง design เป็น Markdown ใน code block โดยมีข้อจำกัดดังนี้:
- deploy บน Cloudflare Workers + Hono (TypeScript) + D1 (SQLite) free plan ห้ามใช้บริการที่ต้องผูกบัตร
- มี starter แล้ว: ตาราง users (role admin/user), sessions, API ล็อกอิน, middleware requireAuth / requireAdmin
หัวข้อ:
1) แผนภาพสถาปัตยกรรมแบบข้อความ (เบราว์เซอร์ → Worker → D1)
2) ADR อย่างน้อย 1 ข้อ เรื่องที่ deploy/tech stack: บริบท, ตัวเลือก 3 แบบ, ตัดสินใจ, เหตุผล, ผลที่ตามมา
   และ ADR เรื่องจะตรวจกติกาเวลาซ้อนที่ไหนและอย่างไร
3) entity + ความสัมพันธ์ และตารางใหม่ (คอลัมน์, ชนิด, constraint, มาจาก FR ไหน)
4) รายการ API: method | path | use case | สิทธิ์ (ใครเรียกได้)
5) ตาราง NFR → การออกแบบ
  1. เปิดไฟล์ docs/DESIGN.md แล้ววางแต่ละส่วนลงหัวข้อที่ตรงกัน:
ส่วนในคำตอบ AIวางลงใน DESIGN.md
1) แผนภาพสถาปัตยกรรม## 2. สถาปัตยกรรม (ใต้แผนภาพเดิม ตรง “ส่วนประกอบที่ต้องเพิ่ม”)
2) ADR## 3. การตัดสินใจทางสถาปัตยกรรม (ADR) แทนแม่แบบ ADR-01
3) entity + ตาราง## 4. ข้อมูล
4) รายการ API## 5. API
5) NFR → การออกแบบ## 6. NFR → การออกแบบ
🔍 ตรวจก่อนไปต่อ

AI เสนอบริการที่ต้องผูกบัตร (เช่น R2, Email, Access) หรือสร้างตารางผู้ใช้และระบบล็อกอินใหม่ซ้ำกับที่ starter มีไหม — ถ้ามี ให้ลบส่วนนั้น แล้วพิมพ์บอก AI ว่า “starter มีระบบผู้ใช้แล้ว ใช้ของเดิม”

✅ ผ่านรอบนี้เมื่อ

docs/DESIGN.md มีแผนภาพ · ADR อย่างน้อย 1 ข้อที่มีตัวเลือกและเหตุผล · ตารางข้อมูลใหม่ (เช่น รถ การจอง) · รายการ API พร้อมสิทธิ์

รอบ 8 · ให้ AI ช่วยรีวิว แต่คุณเป็นคนตัดสิน (3 นาที)

🎯 ทำขั้นนี้เพื่ออะไร

ให้ AI ช่วยหาจุดอ่อนอีกรอบ แต่คุณเป็นคนเลือกว่าจะแก้ข้อไหน เพราะ AI ไม่รู้ว่าเจ้าของโจทย์ตอบอะไรนอกแชตนี้

  1. คัดลอก prompt นี้ไปส่งในแชตเดิม
รีวิว SRS ทั้งหมดที่เราเขียนในแชตนี้ ตอบเป็นรายการสั้น ๆ ไม่เกิน 8 ข้อ:
- requirement ที่กำกวมหรือตรวจไม่ได้
- requirement ที่ขัดกันเอง
- requirement ที่ไม่มีที่มาจากโจทย์หรือคำตอบ (อาจถูกแต่งขึ้น)
- กรณีผิดปกติที่ยังไม่มี AC รองรับ
ห้ามเขียน SRS ใหม่ทั้งหมด
  1. อ่านทีละข้อ ถ้าเห็นด้วย ให้ไปแก้ในไฟล์เอง (ไม่ต้องให้ AI เขียนใหม่) ถ้าไม่เห็นด้วย ข้ามได้
✅ ผ่านรอบนี้เมื่อ

แก้ไฟล์ตามข้อที่เห็นด้วยอย่างน้อย 1 ข้อ และบอกได้ว่าข้อที่ไม่แก้ เพราะอะไร

เช็กคุณภาพ requirement (ทำเอง 2 นาที)

ไล่ตารางนี้กับ FR และ NFR ของคุณ ข้อไหนไม่ผ่านให้แก้ในไฟล์

คุณสมบัติถามตัวเองตัวอย่างที่ไม่ผ่าน → ผ่าน
ไม่กำกวมคนสองคนอ่านแล้วเข้าใจตรงกันไหม“ห้ามจองชน” → “ห้ามจองรถคันเดียวกันที่ช่วงเวลาทับกัน” + ระบุให้ชัดว่าต่อคิวพอดีนับว่าทับไหม (ยังไม่รู้ → ถามเจ้าของโจทย์)
ตรวจสอบได้มีวิธีพิสูจน์ว่าผ่าน/ไม่ผ่านไหม“ใช้บนมือถือได้” → “ทุกหน้าใช้ได้บนจอ 375px ไม่มี scroll แนวนอน”
มีที่มาบอกได้ไหมว่ามาจาก B# หรือ Q# ไหน“ส่ง LINE แจ้งเตือน” (ไม่มีในโจทย์) → ติด [สมมติฐาน] หรือตัดออก
ไม่ขัดกันมีสองข้อที่ทำพร้อมกันไม่ได้ไหม“ยกเลิกได้ทุกเมื่อ” กับ “ยกเลิกได้ก่อนเวลาเริ่ม”
ครบกรณีผิดปกติมี AC รองรับไหมมีแต่ “จองได้” ไม่มี “จองไม่ได้เพราะ…”
จัดลำดับแล้วรู้ไหมว่าข้อไหนต้องมีในรอบแรกทุกข้อเป็น “ต้องมี” → แยก ต้องมี / ควรมี / ยังไม่ทำ
