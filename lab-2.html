ชื่อระบบ: ระบบจองรถส่วนกลาง
ข้อมูลเพิ่มเติม: ระบบผู้ใช้ ล็อกอิน และ admin จัดการบัญชี มีอยู่แล้วจาก starter ไม่ต้องเขียนใหม่ · ต้องใช้ Cloudflare free plan ไม่ผูกบัตร

ใช้หัวข้อตามนี้ทุกหัวข้อ ห้ามเปลี่ยนชื่อหัวข้อ:
# SRS — Software Requirements Specification: [ชื่อระบบ]
## 1. บทนำ  (วัตถุประสงค์ · ขอบเขต · เอกสารอ้างอิง)
## 2. ผู้มีส่วนได้ส่วนเสีย (Stakeholders) และผู้ใช้  (ตาราง: กลุ่ม | บทบาท/สิ่งที่ต้องการ | ใช้ระบบไหม)
## 3. Use Cases  (### 3.1 รายการ use case: รหัส | ชื่อ | ผู้ใช้ · ### 3.2 รายละเอียด use case หลัก: ผู้ใช้, เงื่อนไขก่อนเริ่ม, ขั้นตอนปกติ, กรณีผิดปกติ, ผลลัพธ์)
## 4. Functional Requirements (FR)  (ตาราง: รหัส | ระบบต้อง... | ที่มา | ความสำคัญ | use case)
## 5. Non-functional Requirements (NFR)  (ตาราง: รหัส | ด้าน | เกณฑ์ที่วัดได้ | วิธีตรวจ | ที่มา)
## 6. ข้อจำกัดและสมมติฐานที่ยืนยันแล้ว (Constraints)
## 7. นอกขอบเขต (Out of Scope)
## 8. คำถามที่ยังเปิดอยู่ / สมมติฐานที่รอยืนยัน  (ตาราง: # | คำถาม หรือ [สมมติฐาน] | ถามใคร | คำตอบ — ใส่คำถามและคำตอบทุกข้อที่ฉันให้ไว้)
## 9. ตารางตามรอย (Traceability)  (ตาราง: FR | use case | AC | เคสทดสอบ | ผล — ช่องเคสทดสอบและผลเว้นว่าง)

กติกา:
- FR เขียนข้อละ 1 ความสามารถ ขึ้นต้นด้วย "ระบบต้อง" ตรวจได้ว่าทำแล้วหรือยัง อย่างน้อย 8 ข้อ
- ทุก FR และ NFR ต้องมีที่มา (B# = ย่อหน้าในบันทึก, Q# = คำตอบของเจ้าของโจทย์) ถ้าไม่มีที่มาให้เขียน [สมมติฐาน] ห้ามแต่งที่มา
- ความสำคัญใช้คำว่า ต้องมี / ควรมี / อาจทำ / ยังไม่ทำ — สิ่งที่เจ้าของโจทย์ยังไม่แน่ใจ ใส่ ควรมี หรือ ยังไม่ทำ
- NFR อย่างน้อย 3 ข้อ ต้องวัดได้ (มีตัวเลขหรือผ่าน/ไม่ผ่าน) และบอกวิธีตรวจ: ทดสอบ / สาธิต / ตรวจดู / วิเคราะห์
- use case หลักเขียนละเอียด รวมกรณีผิดปกติทุกกรณีที่โจทย์และคำตอบพูดถึง
- ห้ามเพิ่มความต้องการที่บันทึกและคำตอบไม่ได้พูดถึง

  2. ใน VS Code เปิด docs/SRS.md กด Ctrl+A แล้ว Ctrl+V (วางทับทั้งไฟล์) แล้ว Ctrl+S
📖 ทำไมต้องทำขั้นนี้

SRS (Software Requirements Specification) คือเอกสารรวมความต้องการของระบบเป็นข้อ ๆ ทุกข้อตรวจได้ว่าทำแล้วหรือยัง และตามรอยได้ว่ามาจากย่อหน้าไหน (B#) หรือคำตอบข้อไหน (Q#) — FR คือสิ่งที่ระบบต้องทำได้ NFR คือคุณภาพที่วัดได้ เช่น ใช้บนมือถือจอ 375px ได้ ที่บังคับหัวข้อตามแม่แบบ เพื่อให้ตอนบ่ายเทียบกับฉบับอ้างอิงได้ทีละบรรทัด อ่านเพิ่มในทฤษฎี 2

จาก SRS และ design ที่เราทำในแชตนี้ เขียน SPEC.md ฉบับเต็มกลับมา ส่งทั้งไฟล์ใน code block เดียว โดย:
1) คงส่วน "### ✅ ส่วนที่ starter มีให้แล้ว" ไว้เหมือนเดิมทุกตัวอักษร ห้ามแก้ ห้ามลบ ห้ามเปลี่ยนรหัส AC
2) แทนแม่แบบใต้ "### ✍️ ส่วนของโจทย์ (เติมเอง)" ด้วย user story (US-1, US-2, …) ของ FR ระดับ "ต้องมี"
   แต่ละ story มี acceptance criteria แบบ Given / When / Then ขึ้นต้นด้วยรหัสตัวหนา เช่น **AC-1.1**
   ผลต้องตรวจได้ (HTTP status เช่น 201 400 401 403 404 409 หรือสิ่งที่เห็นบนหน้าจอ) และอ้าง FR ในวงเล็บ
3) ตารางตัวอย่างกติกาเวลาจองซ้อน: สมมติรถ A ถูกจอง 10:00–12:00 ไว้แล้ว ให้ 8 กรณีการจองใหม่
   (ทับบางส่วน, อยู่ข้างใน, คลุมทั้งช่วง, ต่อคิวพอดี, คนละคัน ฯลฯ) กรณีที่ยังไม่ได้ตัดสินให้เขียนว่า "ต้องถามเจ้าของโจทย์"
4) เติมหัวข้ออื่นที่ยังเป็น [ ] ให้ครบจาก SRS และ design (ชื่อแอป เป้าหมาย คำศัพท์ Data Model API NFR นอกขอบเขต คำถามเปิด)
   โดยเก็บแถวที่เป็นของ starter ไว้ (เช่น ตาราง users, sessions และ API /api/auth, /api/users)
ห้ามเปลี่ยนชื่อหัวข้อ

# SPEC — [ชื่อแอป]

> **SPEC.md = ข้อกำหนดฉบับย่อสำหรับ agent** (ฉบับเต็มสำหรับคนอยู่ใน `docs/SRS.md` และ `docs/DESIGN.md`)

>
> กติกาของ AC (acceptance criteria):
> - เขียนแบบ **Given / When / Then** · 1 ข้อ = ตรวจได้ 1 เรื่อง · มีผลที่คาดหวังเป็นรูปธรรม (status, ข้อมูล)
> - รหัส AC เขียนเป็น**ตัวหนา**แบบในส่วน starter ด้านล่าง — `npm run trace` นับเฉพาะรหัสตัวหนาและตรวจว่าทุก AC มีเคสทดสอบ
> - อ้างที่มาจาก SRS ในวงเล็บ เช่น `(FR-03)` — ทำให้ตามรอยได้ว่า AC นี้มาจากความต้องการข้อไหน

## 3. User Stories + Acceptance Criteria

### ✅ ส่วนที่ starter มีให้แล้ว (ตัวอย่าง spec ที่ตรวจสอบได้ — ห้ามลบ)

#### US-0 ตรวจสถานะระบบ
ในฐานะผู้ดูแลระบบ ฉันต้องการเช็กว่าเซิร์ฟเวอร์และฐานข้อมูลพร้อม เพื่อรู้ว่าปัญหาอยู่ที่ระบบหรือที่เครือข่าย
- **AC-0.1** Given เซิร์ฟเวอร์ทำงานและรัน migration แล้ว When `GET /api/health` Then ได้ 200 `{ ok: true, db: "ready" }`

#### US-A1 ตั้งค่าครั้งแรก
ในฐานะผู้ติดตั้งระบบ ฉันต้องการสร้างผู้ดูแลระบบคนแรกจากหน้าเว็บ เพื่อเริ่มใช้งานได้โดยไม่ต้องแก้ฐานข้อมูลเอง
- **AC-A1.1** Given ระบบยังไม่มีผู้ใช้ When `POST /api/auth/setup` ด้วยชื่อและรหัสที่ถูกกติกา Then ได้ 201, ผู้ใช้นั้นเป็น `admin` และล็อกอินอยู่ทันที
- **AC-A1.2** Given ระบบมีผู้ใช้อย่างน้อย 1 คน When `POST /api/auth/setup` Then ได้ 409 (ตั้งค่าซ้ำไม่ได้)

#### US-A2 เข้าสู่ระบบ / ออกจากระบบ
ในฐานะผู้ใช้ ฉันต้องการเข้าสู่ระบบด้วยชื่อและรหัสผ่าน เพื่อใช้งานในนามของตัวเอง
- **AC-A2.1** Given ชื่อและรหัสถูก When `POST /api/auth/login` Then ได้ 200 และ cookie `session` แบบ HttpOnly
- **AC-A2.2** Given รหัสผิด หรือไม่มีชื่อนี้ When ล็อกอิน Then ได้ 401 ด้วย**ข้อความเดียวกัน**ทั้งสองกรณี
- **AC-A2.3** Given ไม่ได้ล็อกอิน When `GET /api/auth/me` Then ได้ 401
- **AC-A2.4** Given ล็อกอินอยู่ When `POST /api/auth/logout` Then session เดิมใช้ไม่ได้อีก (`/api/auth/me` ได้ 401)

#### US-A3 เปลี่ยนรหัสผ่านของตัวเอง
ในฐานะผู้ใช้ ฉันต้องการเปลี่ยนรหัสผ่านเอง เพื่อดูแลความปลอดภัยของบัญชี
- **AC-A3.1** Given ใส่รหัสเดิมถูก และรหัสใหม่ยาว 8–100 ตัว When `PUT /api/auth/password` Then ได้ 200 และล็อกอินด้วยรหัสใหม่ได้
- **AC-A3.2** Given ใส่รหัสเดิมผิด When เปลี่ยนรหัส Then ได้ 400 และรหัสไม่เปลี่ยน

#### US-A4 จัดการผู้ใช้ (admin)
ในฐานะผู้ดูแลระบบ ฉันต้องการเพิ่ม แก้ role ตั้งรหัสใหม่ และลบผู้ใช้ เพื่อควบคุมว่าใครเข้าระบบได้
- **AC-A4.1** Given ผู้ใช้ role `user` When เรียก `/api/users` ใด ๆ Then ได้ 403
- **AC-A4.2** Given admin When `POST /api/users` (ชื่อ, รหัส, role ไม่บังคับ) Then ได้ 201, role เริ่มต้นเป็น `user` และคำตอบไม่มี `password_hash`
- **AC-A4.3** Given มีชื่อผู้ใช้นี้แล้ว When เพิ่มชื่อซ้ำ Then ได้ 409
- **AC-A4.4** Given admin ตั้งรหัสใหม่ให้ผู้ใช้ X When X ใช้ session เดิม Then ได้ 401 และ X ล็อกอินด้วยรหัสใหม่ได้
- **AC-A4.5** Given admin When ลบบัญชีตัวเอง Then ได้ 409 · When ลบผู้ใช้อื่น Then ได้ 200
- **AC-A4.6** Given มี admin เหลือคนเดียว When เปลี่ยน role ของเขาเป็น `user` Then ได้ 409

  3. ดูแถว “ต่อคิวพอดี” ในตารางตัวอย่าง: ตรงกับคำตอบของเจ้าของโจทย์ไหม ถ้าไม่ได้ถามเรื่องนี้ ควรเขียนว่า “ต้องถามเจ้าของโจทย์”
📖 ทำไมต้องทำขั้นนี้

เกณฑ์ตรวจรับเขียนแบบ Given / When / Then (สถานการณ์ตั้งต้น / สิ่งที่ผู้ใช้ทำ / ผลที่ต้องเห็น) ส่วนตารางตัวอย่างช่วยให้เห็นกรณีที่ซ่อนอยู่ เช่น การจองที่เริ่มตรงกับเวลาที่อีกคนคืนรถพอดี ที่ใช้ npm run trace ตรวจ เพราะเป็นวิธีที่เครื่องตรวจให้ได้ทันทีว่ารหัส AC ในเอกสารตรงกับเคสทดสอบ ไม่ต้องอ่านเองทีละบรรทัด อ่านเพิ่มในทฤษฎี 2

7 · บันทึกงานลง Git (3 นาที)

ใช้หัวข้อตามนี้ทุกหัวข้อ ห้ามเปลี่ยนชื่อหัวข้อ:
# SRS — Software Requirements Specification: [ชื่อระบบ]
## 1. บทนำ  (วัตถุประสงค์ · ขอบเขต · เอกสารอ้างอิง)
## 2. ผู้มีส่วนได้ส่วนเสีย (Stakeholders) และผู้ใช้  (ตาราง: กลุ่ม | บทบาท/สิ่งที่ต้องการ | ใช้ระบบไหม)
## 3. Use Cases  (### 3.1 รายการ use case: รหัส | ชื่อ | ผู้ใช้ · ### 3.2 รายละเอียด use case หลัก: ผู้ใช้, เงื่อนไขก่อนเริ่ม, ขั้นตอนปกติ, กรณีผิดปกติ, ผลลัพธ์)
## 4. Functional Requirements (FR)  (ตาราง: รหัส | ระบบต้อง... | ที่มา | ความสำคัญ | use case)
## 5. Non-functional Requirements (NFR)  (ตาราง: รหัส | ด้าน | เกณฑ์ที่วัดได้ | วิธีตรวจ | ที่มา)
## 6. ข้อจำกัดและสมมติฐานที่ยืนยันแล้ว (Constraints)
## 7. นอกขอบเขต (Out of Scope)
## 8. คำถามที่ยังเปิดอยู่ / สมมติฐานที่รอยืนยัน  (ตาราง: # | คำถาม หรือ [สมมติฐาน] | ถามใคร | คำตอบ — ใส่คำถามและคำตอบทุกข้อที่ฉันให้ไว้)
## 9. ตารางตามรอย (Traceability)  (ตาราง: FR | use case | AC | เคสทดสอบ | ผล — ช่องเคสทดสอบและผลเว้นว่าง)

กติกา:
- FR เขียนข้อละ 1 ความสามารถ ขึ้นต้นด้วย "ระบบต้อง" ตรวจได้ว่าทำแล้วหรือยัง อย่างน้อย 8 ข้อ
- ทุก FR และ NFR ต้องมีที่มา (B# = ย่อหน้าในบันทึก, Q# = คำตอบของเจ้าของโจทย์) ถ้าไม่มีที่มาให้เขียน [สมมติฐาน] ห้ามแต่งที่มา
- ความสำคัญใช้คำว่า ต้องมี / ควรมี / อาจทำ / ยังไม่ทำ — สิ่งที่เจ้าของโจทย์ยังไม่แน่ใจ ใส่ ควรมี หรือ ยังไม่ทำ
- NFR อย่างน้อย 3 ข้อ ต้องวัดได้ (มีตัวเลขหรือผ่าน/ไม่ผ่าน) และบอกวิธีตรวจ: ทดสอบ / สาธิต / ตรวจดู / วิเคราะห์
- use case หลักเขียนละเอียด รวมกรณีผิดปกติทุกกรณีที่โจทย์และคำตอบพูดถึง
- ห้ามเพิ่มความต้องการที่บันทึกและคำตอบไม่ได้พูดถึง

ต่อด้วย prompt ของขั้น 4–6 ได้เลย (แก้ชื่อระบบและข้อจำกัดให้ตรงกับงานของคุณ)

อาการวิธีแก้
AI เขียน SRS ยาวทั้งเล่มตั้งแต่ขั้น 1พิมพ์ว่า “หยุด ทำแค่ 3 อย่างที่ขอ: สรุป ผู้เกี่ยวข้อง และคำถาม 5 ข้อ”
AI ไม่ได้ส่งไฟล์ในกล่องโค้ดพิมพ์ว่า “ส่งทั้งไฟล์ใน code block เดียว”
ไฟล์ยาวจนคำตอบขาดกลางทางพิมพ์ว่า “ส่งต่อจากหัวข้อ …” แล้วนำไปวางต่อท้ายในไฟล์
AI เปลี่ยนชื่อหัวข้อ หรือเพิ่มเรื่องที่ไม่ได้คุยกันพิมพ์ว่า “ใช้หัวข้อตามที่ให้ไว้ทุกตัวอักษร และห้ามเพิ่มเรื่องที่บันทึกไม่ได้พูดถึง” แล้วขอใหม่
AI เสนอ Firebase / AWS / ส่งอีเมล / OTPพิมพ์ว่า “ใช้ Cloudflare free plan ไม่ผูกบัตร และมีระบบล็อกอินจาก starter แล้ว”
AI ตอบช้า / ใช้ไม่ได้สลับไปอีกเจ้า (Gemini ↔ ChatGPT) เปิดแชตใหม่ แล้วเริ่มจากขั้น 1 ใหม่ (ใช้คำตอบของเจ้าของโจทย์จากโน้ตเดิม)
