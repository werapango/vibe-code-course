📖 แนวคิดหลัก

เมื่อ AI เขียนโค้ดแทนได้ ส่วนที่ยากที่สุดจึงไม่ใช่การเขียนโค้ด แต่เป็นการ “บอกให้ชัดว่าต้องการอะไร” และ “ตรวจให้แน่ใจว่าสิ่งที่ได้ถูกต้อง” วันนี้จึงฝึกทั้ง validation (ตรวจว่า spec ตรงกับความต้องการจริงของผู้ใช้ไหม) และ verification (ตรวจว่าโค้ดทำงานตรงตาม spec ไหม)

จุดประสงค์การเรียนรู้

  1. อธิบาย SDLC และบอกได้ว่าแต่ละขั้น (phase) ได้ผลงานอะไรออกมา และ AI เข้ามาช่วยหรือเปลี่ยนอะไร
  2. หาความต้องการจริง: ระบุ stakeholder (ผู้ที่เกี่ยวข้องกับระบบ) ถามเจ้าของโจทย์ เขียน use case, user story และ FR/NFR (ความต้องการด้านฟังก์ชัน / ด้านคุณภาพ) ที่มีที่มาและวัดได้
  3. เขียน Spec ที่ตรวจสอบได้: acceptance criteria (AC: เกณฑ์ตรวจรับ) แบบ Given/When/Then (กำหนดให้… เมื่อ… แล้วต้อง…), ตารางตัวอย่าง และตามรอยว่าทุก requirement มี test ด้วย npm run trace
  4. ออกแบบเบื้องต้น: สถาปัตยกรรม ที่ที่จะ deploy, tech stack, ข้อมูล, API และบันทึกเหตุผลของการตัดสินใจเป็น ADR (Architecture Decision Record)
  5. แตกงานเป็น WBS และใช้ Agent & Skill ให้ทำงานทีละ task อย่างมีวินัย (เข้าใจ ADLC — วงจรการพัฒนา agent และ skill)
  6. ใช้คำสั่ง Cloudflare เอง ตั้งแต่สร้างโปรเจกต์ ฐานข้อมูล migration (เปลี่ยนโครงสร้างตาราง) deploy (นำขึ้นออนไลน์) rollback (ย้อนเวอร์ชัน) จนตรวจ log

ละเอียดรายช่วง: ตารางเวลา

หลักการ 5 ข้อ

1 · คำสั่ง Cloudflare คนพิมพ์เอง

สร้างโปรเจกต์ ฐานข้อมูล migration deploy rollback — agent ห้ามรันคำสั่งแทน (กติกานี้เขียนไว้ในไฟล์ AGENTS.md ที่ agent อ่านทุกครั้ง)

2 · ทุก requirement มีที่มา

มาจากโจทย์หรือคำตอบของเจ้าของโจทย์ ข้อที่ AI เดาเองติดป้าย [สมมติฐาน] จนกว่าจะยืนยัน

3 · ทุก AC ตรวจได้

AC ทุกข้อเขียนแบบ Given/When/Then ที่ตรวจผลได้ชัดเจน และทุกข้อมี smoke test (สคริปต์ที่เรียก API จริงเพื่อทดสอบ) โดยใช้ npm run trace ตรวจว่าครบไหม

4 · สั่งงานครั้งละ 1 task

สั่ง agent ทีละ task จาก TASKS.md เช่น ทำ task T1.1 ใน TASKS.md แล้วคนตรวจ diff (ส่วนที่โค้ดเปลี่ยน) ก่อน commit

5 · Deploy ให้เร็ว และย้อนกลับได้

ได้ URL จริงตั้งแต่ชั่วโมงแรก และรู้วิธี rollback ก่อนจะต้องใช้จริง
